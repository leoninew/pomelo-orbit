# CD 应用创建方式选择需求
最后修改时间: 2026-06-27 00:00:51

Review status: Accepted

## Background / 背景

当前应用管理的“新建应用”入口只创建应用元信息，表单只包含应用名称、应用代码、镜像拉取策略和路由托管开关。创建后的应用默认没有 `docker-compose.yml` 或其他配置文件，用户仍需要进入详情页手动补齐部署配置。

这对熟悉 Docker Compose 的高级用户可用，但对常见的单服务镜像部署场景不友好。前置分析 `docs/analyze/application-management-usability.md` 中已将 P1 定义为“把新建应用改成创建方式选择”，目标是在不废弃现有配置文件模型的前提下，用向导层生成可部署配置，降低用户创建可部署应用的成本。

本次采用标准模式 / standard，当前阶段只定义需求，不写产品代码。

## Goal / 目标

1. 将应用列表页当前“新建应用”入口调整为更贴近用户预期的“创建应用”流程。
2. 创建流程第一步提供创建方式选择：
   - 从镜像创建
   - 从 docker-compose 创建
   - 导入应用包
   - 高级空白应用
3. 使用 Reka UI 的 Stepper 组件呈现多步骤创建流程。
4. 优先完整落地“从镜像创建”路径，让最常见的单服务应用可以通过表单生成可部署配置。
5. 保留并整合现有高级能力：docker-compose 配置文件、JSON 应用包导入、空白应用创建。
6. 底层仍沿用现有 backend-go 的应用、配置文件、路由、导入导出和部署模型，不引入新的部署执行链路。

## Non-goal / 非目标

1. 不实现完整应用市场或模板库。
2. 不重构现有 `application`、`application_config_file`、`application_service`、`application_route` 数据模型。
3. 不修改已执行的数据库迁移文件。
4. 不处理旧 Python backend，本功能只面向当前 backend-go。
5. 不在本阶段实现部署预检、部署失败智能诊断或 `.env` 专用编辑器。
6. 不移除高级用户手写 docker-compose 和自由配置文件的能力。
7. 不自主启动、停止或重启开发服务器。

## User scenarios / 用户场景

### 场景 1：普通用户从镜像创建单服务应用

用户希望部署一个已有镜像，只知道镜像名和容器端口。用户点击“创建应用”，选择“从镜像创建”，填写应用名称、应用代码、镜像、容器端口，可选填写环境变量、数据目录、域名/路由，提交后系统创建应用并生成可部署的配置文件。

期望结果：用户无需手写 `docker-compose.yml`，创建完成后应用具备部署所需的基础配置。

### 场景 2：已有 docker-compose 的用户创建应用

用户已有 compose 内容，希望继续使用自己的编排文件。用户点击“创建应用”，选择“从 docker-compose 创建”，粘贴 compose 内容，系统保存为应用配置文件，并保留后续解析 service、镜像和路由的能力。

期望结果：用户可以沿用已有 compose，不被强制拆成镜像表单。

### 场景 3：用户导入已有应用包

用户已有 Pomelo Orbit 导出的 JSON 应用包。用户点击“创建应用”，选择“导入应用包”，上传或选择文件，确认应用名称、应用代码和导入摘要后完成创建。

期望结果：现有导入能力仍可用，但入口归并到统一创建流程中。

### 场景 4：高级用户创建空白应用

高级用户明确希望手动维护配置文件。用户点击“创建应用”，选择“高级空白应用”，填写当前已有基础字段后创建空白应用。

期望结果：当前“只创建元信息”的能力保留，但用户已明确选择高级模式，不再误以为默认创建的是可部署应用。

## Functional requirements / 功能需求

### 1. 创建入口与第一步方式选择

- 应用列表页主按钮文案应调整为“创建应用”。
- 点击后跳转到独立创建路由和页面，不在应用列表页停留，不使用创建模态窗。
- 创建流程第一步必须展示 4 种创建方式：
  1. 从镜像创建
  2. 从 docker-compose 创建
  3. 导入应用包
  4. 高级空白应用
- 每种方式应有简短说明，帮助用户理解适用场景。
- 选择方式后进入对应后续步骤。

### 2. Stepper 交互

- 创建流程使用 Reka UI Stepper 组件呈现步骤进度。
- Stepper 应表达当前步骤、已完成步骤和后续步骤。
- 用户可在合理范围内返回前一步修改选择或表单。
- 不允许绕过必填步骤直接提交。
- 页面层使用 Reka UI 时应保持与项目现有风格一致；如需要封装共享组件，应在 Plan 阶段明确。

### 3. 从镜像创建

用户输入字段：

- 应用名称：必填。
- 应用代码：必填，沿用当前应用代码格式约束。
- 镜像：必填，例如 `nginx:1.27`。
- 容器端口：必填，表示容器内部监听端口。
- 环境变量：可选，允许填写 key/value 列表，并落盘为 `.env`。
- 数据目录：可选，支持配置多条宿主侧数据目录与容器内目录的映射。
- 域名/路由：可选，用户填写域名后系统启用路由托管并创建路由配置。

系统生成：

- `docker-compose.yml` 配置文件。
- 当存在环境变量时，生成 `.env`，并在 compose 中通过 `env_file: .env` 显式引用，确保容器能获得这些环境变量，避免用户误解 `.env` 自动注入容器。
- 当填写域名/路由时，创建应用路由配置，并确保 `route_managed` 为 true。
- 当未填写域名/路由时，不强制启用路由托管。

生成的 compose 至少应包含一个 service，service 名称可由应用代码派生或在 Plan 阶段确定。生成结果需要能被现有部署链路识别，并支持后续详情页的 compose service 解析、镜像配置和路由托管能力。

### 4. 从 docker-compose 创建

- 第一阶段展示该创建方式，但本次实现不落地该路径的完整提交能力。
- 用户选择该方式时，应看到“后续支持”或等价提示，不应进入不可用或半成品的提交流程。
- 不在本次实现 compose 粘贴、上传、解析摘要或保存逻辑。

### 5. 导入应用包

- 第一阶段展示该创建方式，但本次实现不迁移现有独立导入入口到 Stepper 流程。
- 当前 JSON 导入能力可以继续保留在现有入口中，避免本次 P1 从镜像创建范围扩散。
- 用户选择该方式时，应看到“后续支持”或等价提示，不应破坏现有导入能力。

### 6. 高级空白应用

- 第一阶段展示该创建方式，并在独立创建页面内进入原高级空白创建表单。
- 高级空白应用仍按原字段和原创建接口创建应用，不额外生成配置文件。
- 当前空白创建能力按原实现语义保留，不应破坏现有高级空白创建能力。

## Acceptance criteria / 验收标准

1. 应用列表页主创建入口跳转到独立创建应用页面。
2. 创建流程第一步展示 4 种创建方式。
3. 创建流程使用 Reka UI Stepper 组件实现步骤展示。
4. 本次可完整提交的创建方式限定为“从镜像创建”。
5. “从镜像创建”可以填写应用名称、应用代码、镜像、容器端口，并能创建出包含 `docker-compose.yml` 的应用。
6. “从镜像创建”填写环境变量时，系统生成 `.env`，并在 `docker-compose.yml` 中通过 `env_file: .env` 显式引用，使容器获得这些环境变量。
7. “从镜像创建”支持多条数据目录映射，并写入 `docker-compose.yml` 的 service volumes。
8. “从镜像创建”填写域名/路由时，创建后的应用启用路由托管，并创建对应路由配置。
9. 前端串联创建应用、创建配置文件、创建路由等现有接口时，必须处理某一步失败后用户重新提交的场景，避免简单重复提交导致不可恢复或重复数据。
10. “从 docker-compose 创建”“导入应用包”在本次至少作为方式展示并给出后续支持或保持现有入口的说明；“高级空白应用”应在独立创建页面内进入原高级空白创建表单。
11. 前端变更后必须执行 `yarn lint --fix && yarn typecheck` 并通过。
12. backend-go 如新增或调整接口，必须补充相关 Go 测试并通过相关测试。
13. 不修改旧 Python backend，不修改已执行迁移文件。

## Decisions / 已确定决策

1. 当前功能使用标准模式 / standard：Requirement → Plan → Implementation → Verification。
2. 本次功能围绕 P1“创建方式选择”展开，不继续扩大到 P2/P3/P4。
3. UI 框架使用 Reka UI，创建流程在独立页面中使用 Stepper 组件。
4. 底层部署模型不变：向导生成配置文件和路由数据，部署仍走现有 backend-go Docker Compose 链路。
5. 本次完整落地范围限定为“从镜像创建”；其他方式先展示并说明后续支持或保持现有入口。
6. 环境变量落盘为 `.env`，并在 compose 中通过 `env_file: .env` 显式引用。
7. 数据目录支持多条 volume 映射。
8. “从镜像创建”通过前端串联现有接口完成，不新增 backend-go 聚合创建接口；实现必须考虑某步失败后用户重新提交的场景。

## Open questions / 待确认问题

暂无需要用户确认的未决事项。

Plan 阶段仍需细化的实现问题：

1. 前端串联接口时，如何识别“重新提交”是继续补齐同一个已创建应用，还是用户确实要创建另一个同 code 应用。
2. 失败恢复 UI 应展示哪些状态与操作，例如重试、跳转到详情页手动修复、或重新开始。
3. 生成 compose 的 service 名称、volume 格式、`.env` key 校验规则和 YAML 输出格式。

## Risks / 风险

1. 前端串联多个现有接口实现“从镜像创建”，中间任一步失败可能造成应用已创建但配置文件或路由未创建；Plan 阶段必须明确失败恢复和重新提交策略。
2. 因用户已决定不新增 backend-go 聚合接口，本次实现需要接受前端编排带来的非事务性风险，并在 UI/重试逻辑中处理。
3. Stepper 是 Reka UI primitive，项目规范要求页面层优先使用共享组件；若直接在页面中大量使用 primitives，可能需要在 Plan 阶段考虑封装。
4. 从镜像生成 compose 时，如果环境变量、volume、路由默认规则设计不清，可能继续制造隐藏行为；Plan 阶段应优先选择简单、可解释的生成规则。
