# CD 部署详情展示执行命令与容器日志
最后修改时间: 2026-06-30 12:18:00

Review status: Accepted

## Background

当前 `/cd/deployments/{id}` 部署详情页在“基本信息”中展示部署 ID、应用、状态、操作类型、触发方式、耗时和时间信息，但用户仍难以判断本次到底执行了哪一种操作，以及系统实际执行的 Docker Compose 命令是什么。

同时，当前页面下方的日志区域偏向展示 deployment 执行日志 / 操作日志。对于部署、强制重建部署和重启这类容器启动相关操作，用户更关心容器启动后的运行输出，而不是 Orbit 执行 `docker compose` 命令本身的过程日志。因此需要调整部署详情页的信息表达：在基本信息里补充“执行命令”，并将日志展示重点切换为容器日志。

## Goal

- 在部署详情页“基本信息”中增加“执行命令”，让用户清楚看到本次操作实际对应的 Docker Compose 命令。
- 对普通部署、强制重建部署、重启等容器启动/重启类操作，部署详情页展示容器日志，而不是默认展示操作日志。
- 容器日志允许以实时或近实时方式展示，帮助用户观察应用启动后的实际运行状态。
- 容器日志区域提供类似流水线详情页 `/ci/run/{id}` 的自动刷新 / 暂停刷新能力；进入运行中的部署或重启详情时默认开启自动刷新，进入已完成或失败等终态详情时只拉取一次日志，不自动刷新。
- 保留现有部署详情页的基础信息、状态、取消和返回逻辑；容器日志区域不保留独立的原“刷新”按钮。
- 页面文案避免把所有操作都固定称为“部署日志”，减少停止/重启场景下的语义误导。

## Non-goal

- 不把操作日志作为页面主要日志内容展示。
- 不在本需求中重做整个部署详情页信息架构或视觉风格。
- 不主动启动、停止或重启开发服务器。
- 不改变应用列表页、应用详情页的操作入口设计。
- 不改变 Docker Compose 实际执行行为；本需求只调整详情页可见信息与日志展示。
- 不要求在本需求中实现完整的历史日志归档系统。

## User scenarios

1. 用户从应用详情页触发普通部署后进入部署详情页，可以在“基本信息”中看到实际执行命令，例如 `docker compose -f docker-compose.yml up -d --remove-orphans --pull missing`，并看到容器启动日志。
2. 用户触发强制重建部署后进入部署详情页，可以看到执行命令包含 `--force-recreate`，并能观察新容器启动后的实时或近实时日志。
3. 用户触发重启后进入详情页，可以看到执行命令为 `docker compose -f docker-compose.yml restart`，并能观察重启后的容器日志。
4. 用户查看停止类操作详情时，页面不应误导性地展示“部署日志”；如果容器日志不适用于该操作，应给出明确说明或展示可用的最近容器日志上下文。
5. 用户刷新部署详情页、从部署列表进入详情页或打开分享链接时，仍应能看到本次操作的执行命令，不能依赖一次性的 URL query 参数。
6. 用户进入运行中的部署或重启详情页后，容器日志默认自动刷新；用户可以暂停刷新以阅读当前日志，也可以再次开启自动刷新。
7. 用户进入已完成或失败的部署或重启详情页后，页面只拉取一次容器日志，不默认开启自动刷新；用户后续点击自动刷新时，应允许自行开启持续刷新。

## Acceptance

- 部署详情页“基本信息”区域新增“执行命令”字段。
- 普通部署的执行命令不包含 `--force-recreate`。
- 强制重建部署的执行命令包含 `--force-recreate`。
- 重启操作的执行命令展示为对应的 `docker compose restart` 命令。
- 停止操作的执行命令展示为对应的 `docker compose down` 命令；如果删除 volumes，则命令包含 `-v`。
- 执行命令必须作为完整命令字符串持久化，并由部署详情 API 返回；页面不能临时拼接命令，也不能只依赖 `/cd/deployments/{id}?from=application` 之类的 URL query。
- 部署和重启类详情页的日志区域展示容器日志，而不是把操作日志作为主内容。
- 容器日志优先展示“本次操作开始后”的日志，即基于 deployment `started_at` 使用类似 `docker compose logs --since <started_at>` 的时间过滤；区别于“最近 N 行日志”，后者只按行数截取当前 compose 日志尾部，可能包含本次操作前的历史输出。
- 如果由于运行环境、时间戳或 Docker Compose 能力限制无法获取“本次操作开始后”的日志，才允许回退为“最近 N 行日志”，并必须在页面上明确说明日志可能包含历史输出。
- 停止类操作不展示实时容器日志，不应显示误导性的“部署日志”标题；页面需要明确说明“停止操作不展示实时容器日志”。
- 进入运行中的部署或重启详情页时，容器日志默认自动刷新，并提供“自动刷新 / 暂停刷新”切换按钮；暂停后不继续轮询容器日志，再次开启后恢复刷新。
- 进入已完成或失败等终态部署详情页时，容器日志只拉取一次，不自动开启轮询；如果用户点击自动刷新，应允许手动启动并持续刷新，不因终态状态阻止。
- 容器日志区域移除原独立“刷新”按钮；错误态重试可以直接重新拉取容器日志。
- 现有返回应用、返回部署列表、取消运行中任务能力保持可用。
- 前端 lint/typecheck 和 Go fmt/vet/test 按项目约束通过。

## Open questions

暂无必须由用户确认的未决事项。已确认：

- 容器日志优先展示“本次操作开始后”的日志；“最近 N 行日志”仅作为无法按时间范围获取时的回退方案，并且必须明确提示可能包含历史输出。
- 执行命令来源为持久化的完整命令字符串。
- 停止操作详情页不展示实时容器日志。
- 运行中的部署或重启详情默认开启自动刷新，并支持用户手动暂停 / 恢复刷新；已完成或失败等终态详情默认不自动刷新，但用户可以手动开启。

## Decisions

- 使用标准模式 / standard 记录本需求，后续进入 Plan 后再确定具体实现方案。
- 基本信息中只要求新增“执行命令”，不要求新增复杂的“执行详情”卡片。
- 执行命令使用完整命令字符串持久化，并由部署详情 API 返回给前端展示。
- 日志展示重点从操作日志调整为容器日志；操作日志不作为默认主视图。
- 容器日志优先按本次操作开始时间过滤；最近 N 行日志只作为回退展示。
- 停止操作详情页不展示实时容器日志，改为明确说明停止操作不适用。
- `/cd/deployments/{id}?from=application` 中的 `from=application` 只作为返回来源，不作为操作方式或执行命令的数据来源。

## Risk

- 如果回退展示 `docker compose logs --tail N`，可能混入本次操作前的历史日志，需要页面提示避免误导。
- 执行命令需要新增持久化来源，可能涉及迁移、model、repository、API response 和测试更新；Plan 阶段需要设计写入时机，确保记录的是实际执行命令。
- 实时容器日志可能涉及轮询、流式输出或输出量控制，需要避免页面卡顿、请求过频和日志无限增长。
- 停止操作后容器可能不存在，因此本需求明确停止详情不展示实时容器日志，但仍需要避免用户误以为日志加载失败。
