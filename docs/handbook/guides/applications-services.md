# 应用、版本与服务

本文按“定义要运行什么 → 创建运行绑定 → 提交操作 → 检查结果”的顺序，说明普通业务应用的管理路径。对象关系见[核心概念](../concepts/core-model.md)，执行目标准备见[项目与执行环境](./projects-environments.md)。

## 开始前

- 已有可访问且已登录的实例，当前用户有项目及相应操作权限，并选中了正确项目。
- 项目执行环境已配置；执行部署前应完成项目初始化，SSH 目标需有有效凭据和主机指纹。若“部署”将你带回初始化页面，先完成相应准备。
- 已有你能确认来源、架构及使用条件的镜像，目标能访问所需镜像源，并已准备目录、端口、变量和持久化数据方案。
- 如果选择加入 Traefik 网络，先确认当前环境的网关已部署并就绪；网关类应用从专门的网关入口管理，不沿用本文的业务服务部署步骤。

本指南适用于 `develop` 分支。文中的 `orders`、`api` 和 `orders-main` 仅用于解释命名；镜像及其运行配置需要自行准备，不能将这些名称直接当作可部署的应用。

## 创建应用并找到初始版本

1. 打开“持续部署”中的“应用”，点击“创建应用”。填写名称和编码；此入口创建普通业务应用，类型显示为 `standard`，无需另行选择。
2. 编码以小写字母开头，可含小写字母、数字和连字符；使用稳定且可识别的名字，例如 `orders`。
3. 创建后进入应用详情，找到自动生成的初始版本。初始版本标签使用应用编码，状态是 `unpublished`，尚无可运行组件；也可以按需要新建另一个版本。
4. 打开要编辑的版本详情，核对所属应用、标签和状态。

应用只是可部署定义的容器。创建应用或空版本不会创建 Docker 容器，也不会自动生成可以成功部署的业务配置。

## 在未发布版本中声明组件

1. 在版本详情点击“添加组件”，填写组件名、镜像，并选择镜像拉取与重启策略。组件名应在版本内唯一，例如 `api`。
2. 按镜像实际要求配置入口和命令；没有覆盖需求时不要为了填满表单擅自改写镜像默认行为。
3. 保存组件后进入组件详情，按需编辑环境变量、挂载、端口 / 暴露、依赖、健康检查等分组。不同配置组分别保存，离开前确认没有遗漏。
4. 返回版本并点击“预览”，核对生成的 Compose 定义。预览只渲染定义，不拉取镜像、不启动容器，也不证明业务健康。

把同一版本中会一起交付的容器声明作为不同组件，例如 `api` 与 `redis`；不要为每个容器都创建一个管理整个应用的 Service。

声明变量时区分组件配置与服务侧的实际值。版本可以引用服务环境变量，例如 `${SHARED_PASSWORD:?required}`；对应服务必须提供非空的 `SHARED_PASSWORD` 才能形成有效部署计划。变量名和引用必须一致，不要把真实密码写成公开版本示例或贴进问题反馈。

这里仅解析组件环境值中的完整占位符，不展开字符串中间的引用；组件字面覆盖也不会再次解析。默认值的空串差异、继承 / 删除及生成 Compose 的限制见[变量与 Compose 约束](../reference/variables-compose.md)。版本预览不读取某个 Service 的实际值，部署前还需检查服务预览。

配置挂载和端口前，确认数据目录归属、目标平台路径及宿主机端口占用。版本预览不能替代这些运行侧检查，也不能证明某个镜像可以公开拉取。

## 发布与复制版本

| 动作 | 结果 | 不会做什么 |
| --- | --- | --- |
| 发布 | 校验版本至少有一个有效组件，将状态变为 `published`，组件定义不再直接编辑 | 不构建或推送镜像，不部署服务 |
| 复制 | 从已有版本形成新的未发布版本，便于修改并保留原定义 | 不自动切换已有服务，不更新容器 |
| 撤回发布 | 将版本恢复为未发布状态，允许继续编辑 | 不回滚已部署的容器或运行数据 |

推荐先完成配置和预览，再发布；后续改动通过复制形成新版本，更容易区分交付内容。服务也可以选择未发布版本，因此“能在下拉框中选到”不代表版本已经审核或部署验证。

## 创建服务并填写运行配置

1. 打开“持续部署”中的“服务”，点击“创建服务”。
2. 选择应用、该应用下的版本和服务编码。编码在项目内唯一，使用小写字母、数字及连字符，不以连字符开头或结尾，最长 63 位，例如 `orders-main`。
3. 创建后进入服务详情，核对应用、版本和编码。新服务初始为停止状态，这只是已建立运行绑定，不表示曾经部署后又停止。
4. 在服务环境变量中填写版本引用所需的实际值；按需进入服务组件详情，设置该绑定自己的运行覆盖，如命令、运行策略、挂载或端口。更换镜像应修改或选择相应的应用版本，不在这里替换镜像定义。
5. 点击服务的“预览”，检查版本定义与运行覆盖合成后的 Compose。若有效运行配置不可用，先处理缺失变量或无效覆盖，不要靠重复部署跳过错误。

同一应用可以有多个服务，例如 `orders-main` 与 `orders-preview`。它们仍使用项目的同一个执行环境，必须分别安排目录、宿主机端口和数据资源。创建第二个服务不会自动提供隔离的 Docker 主机。

保存服务配置不会即时更新运行容器；编辑服务所选版本同样只是改变绑定。要使预期配置生效，还需提交部署并检查结果。

也可以通过[部署对话](./deployment-dialogue.md)操作已有能力，但需准备 LLM 与对话权限，并了解发送后可直接调用工具、历史按项目共享。模型回答不替代配置核对和本次部署结果；对话不是必经入口，也不提供通用逐项确认或回滚。

## 确认目录并提交部署

1. 在业务服务上点击“部署”，重新核对所选版本。
2. 确认“部署目录”。首次通常建议为环境工作目录下的 `deployment/<服务编码>`；已有服务可能显示之前保存的目录。以实际目标为准，使用目标平台绝对路径或 `~/...` 路径，不含 `..`，不要选择系统根目录或其他服务的目录。
3. 核对拉取策略、是否强制重建，以及是否加入 Traefik 网络。不需要网关网络的独立服务可按实际需求取消加入；需要时先确认网关就绪。
4. 提交后阅读警告并进入对应部署记录。出现“部署任务已创建”只表示受理，不能据此判断容器已经更新。

修改部署目录会改变文件和相对挂载的位置，**旧数据不会自动迁移**。有数据的服务应先安排备份和迁移，不要通过改目录绕过占用或挂载冲突。服务详情中的“运行目录”与待部署目录可能不同，应结合本次部署记录判断实际使用位置。

首次练习可以按[首个应用部署](../getting-started/first-deployment.md)使用无状态服务和回环端口；涉及持久化卷、升级或恢复时，先按[数据保留与升级](../operations/data-upgrades.md)明确数据范围。

若确认窗口打开后环境又被修改，系统可能要求重新确认部署目录。关闭并重新打开部署窗口，核对当前目标和目录后再提交，不沿用旧目标的确认结果。

## 检查本次操作和当前运行状态

一次部署至少检查以下三层，而不是只看某条历史成功记录：

| 检查位置 | 要确认的事实 |
| --- | --- |
| 本次部署记录 | 应用、服务、操作类型、版本和工作目录是否符合预期；等待操作结束，查看状态、日志与错误 |
| 服务详情和组件运行状态 | 是否有更新的操作、容器是否存在且运行、健康检查及实际镜像等信息是否符合预期；有疑问时查看容器日志 |
| 应用自己的访问路径 | 在你已配置的端口或路由上验证业务响应；部署完成不等于 DNS、路由、认证及业务功能都正常 |

服务可能有多次部署、重启或停止记录。当前状态以最新受理的相关操作为准，较早任务成功不应被当成最新操作的结论。

如果容器被外部工具改动，服务列表的“状态检查”可以读取当前环境的容器状态，对比记录状态；审阅差异后再点击“更新状态”。它不会部署或修复容器。遇到查询失败、结果过期或服务 / 环境已变化时，重新检查，不把同步状态当成重新部署。

## 更新、停止与删除

- **更新版本或配置：** 复制或准备新版本，核对组件和服务运行覆盖，预览后重新部署；版本切换若遇到组件或挂载对应关系错误，先修正映射，不通过删除数据绕过。
- **停止：** 在服务中确认停止范围并提交，进入本次记录等待结果。“同时删除 volumes”可能删除持久化数据，无明确清理和备份方案时不要勾选；停止不是数据备份。
- **删除：** 界面只允许删除已停止或失败的服务记录。删除记录不能替代运行侧停机或数据清理；失败状态也不证明所有容器和目录都已清理，先核对执行日志和目标资源。

版本被服务引用时不能直接删除，应用仍有服务绑定时也不能直接删除。先梳理引用与运行资源，不要把删除定义当成回滚部署。

## 遇到失败时

| 症状 | 优先核对 |
| --- | --- |
| 发布失败 | 版本是否至少有一个组件，组件名、镜像、策略及配置是否合法 |
| 服务预览或有效配置报缺变量 | 对应服务是否已填写引用需要的值，必填值是否为空；不要在反馈中暴露敏感值 |
| 部署前提示目标或指纹问题 | 回到[项目与执行环境](./projects-environments.md)核对当前配置、授权和指纹，不切回本机规避 |
| 目录或运行挂载冲突 | 核对其他服务、历史运行目录及正在使用的数据路径；避免目录重叠，先评估数据方案 |
| 任务已创建但最终失败 | 查看本次部署错误及日志，再检查镜像获取、目录权限、端口占用和 Docker / Compose 条件 |
| 容器运行但无法访问 | 区分业务进程、健康检查、宿主机端口与网关 / 路由 / DNS；容器运行不证明整个访问链路正常 |

需要对外访问时，继续阅读[网关、DNS 与路由](./gateway-dns-routes.md)，区分组件端点随部署生成的入口、自定义路由的显式同步和 Cloudflare 记录的外部写入；服务部署成功不能替代这些层次的检查。

需要回顾构建与部署的联系时，返回[项目概览](../getting-started/overview.md)。流水线构建不是使用已有镜像创建业务服务的强制前置，但镜像的真实性、可访问性及部署结果仍需在你的执行环境中验证。

如需由源码构建并形成应用版本，先完成[仓库与仓库凭据](./repositories-credentials.md)，再按[流水线与制品](./pipelines-artifacts.md)检查组件映射和生成版本；构建产物不会自动更新服务。
