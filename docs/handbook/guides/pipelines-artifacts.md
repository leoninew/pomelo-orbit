# 流水线与制品

本文说明怎样组织构建阶段、复用模板、检查运行和制品，以及在满足条件时形成应用版本。源码和认证的前提见[仓库与仓库凭据](./repositories-credentials.md)，执行目标准备见[项目与执行环境](./projects-environments.md)。

## 开始前

- 已有可用且已登录的实例，选中了有操作权限的项目，登记了要使用的共享仓库。
- 项目环境已配置，执行侧的 Docker、Compose、工作目录和网络具备条件；SSH 环境还需有效执行凭据、主机指纹及已配置的 SSH CI 运行支持，源码必须是 HTTPS Git。
- 使用可信的阶段镜像和脚本。执行镜像需包含脚本所需工具；镜像可拉取、Git 认证和镜像仓库权限应分别确认。
- 如需让镜像制品形成应用版本，先准备该项目下的业务应用和来源版本中的组件，见[应用、版本与服务](./applications-services.md)。只运行构建并不强制绑定业务应用。

本指南适用于 `develop` 分支。示意脚本只说明填写方式，执行镜像、仓库访问和推送权限需要按你的目标环境准备并确认。

## 从阶段模板到可运行流水线

| 对象 | 用途 | 作用范围与区别 |
| --- | --- | --- |
| 阶段模板 | 保存执行镜像、脚本和制品声明 | 全局复用定义，不是一次执行记录 |
| 流水线模板 | 引用阶段并组织依赖及变量 | 全局共享，不可直接运行 |
| 应用流水线 | 从模板复用，绑定仓库并按需关联业务应用 | 属于当前项目，有自己的阶段配置，可提交运行 |
| 运行记录 | 保存某次受理的定义快照、变量和执行目标信息 | 用于追踪历史，不等于当前编辑器内容 |

“应用流水线”是流水线类型，不表示必须绑定业务 Application。未绑定业务应用时可以执行和收集制品，但不能使用组件映射来派生该应用的版本。

## 准备阶段与依赖

1. 打开“持续集成”中的“阶段”，新建或选择阶段模板，核对执行镜像、脚本、说明及制品声明。
2. 打开“流水线”，创建或选择流水线模板。在阶段编排中添加阶段，填写合适的名称、排序和依赖。
3. 用依赖关系表达“先取源码，再构建，再检查”等前置条件；排序不是串行执行保证，没有依赖的阶段可能同时执行。不要让它们写入同一输出而没有约束。
4. 配置所需变量并保存，检查不存在循环依赖、缺失依赖或重复制品名称。

平台执行的是阶段脚本，登记仓库本身不会隐式完成 checkout。取源码、检出 ref、构建和推送应由选用的阶段实现；脚本中的 <code v-pre>{{ repository_url }}</code>、<code v-pre>{{ repository_ref }}</code> 等模板变量会在运行中解析，普通 shell 变量语法不要与平台模板混淆。

阶段的 `/workspace` 用于共享工作文件，`/artifacts` 用于本次运行的制品文件。本地目录源码还会以只读方式挂载到 `/source`；它不是任意 SSH 主机都可访问的路径。脚本要区分源码位置、构建工作目录和产物位置，不假定工作区每次都是全新目录。

## 复用为项目流水线

1. 在流水线模板上点击“复用”，进入“创建应用流水线”。
2. 填写名称、选择代码仓库，按需选择业务应用。创建后核对来源模板及其版本、仓库和应用关系，不把共享模板当作项目副本直接运行。
3. 如果绑定业务应用且模板声明了 Docker 镜像制品，选择来源版本策略及组件映射；具体约束见后文。只想先检查脚本或收集文件时，可不绑定业务应用。
4. 在新流水线中核对阶段、依赖和变量。自定义或覆盖变量时确认作用域、值和敏感标记，不能只凭变量名相同就认为各阶段会得到相同值。

修改共享阶段或流水线模板不会悄悄改写已经复用的项目阶段。界面提供“更新至模板”时先预览差异，再显式确认；确认后重新核对私有配置和制品映射。更新模板也不会改变已经生成的历史运行快照。

缺少必需变量可能在创建运行之前就被拒绝。当前运行对话框主要确认分支或标签，其余配置应在仓库或流水线变量区域准备；敏感标记不保证脚本、日志或制品内容自动脱敏。

Liquid 引用、仓库 / 阶段 / 全局优先级、内建上下文及嵌套限制见[变量与 Compose 约束](../reference/variables-compose.md)。阶段的解析值也会作为阶段环境传入，但不等于业务 Service 的容器环境；不要把 shell 或 Compose 默认值语法套入模板字段。

## 最小文件制品配置示意

若要先理解“脚本输出 → 制品记录”的关系，可在隔离环境准备一个最小阶段。以下仅为配置示意，不是完整构建教程，不包含取源码、镜像构建或部署：

1. 自备能在目标上运行、包含 `/bin/sh` 和 `printf` 的可信 Linux 执行镜像，不根据本文推断任何公共标签可用。
2. 在阶段模板的脚本中填写：

```sh
printf 'pipeline smoke check\n' > /artifacts/report.txt
```

3. 在该阶段的“制品声明”添加：名称 `report`，收集器 `file`，引用 `report.txt`。引用相对于本次运行的制品目录，而不是填写容器内完整的 `/artifacts/report.txt`。
4. 将阶段加入流水线模板，复用并绑定一个已有仓库，不绑定业务应用；核对环境及变量后再由你决定是否运行。
5. 如果运行，预期检查阶段退出码、完整运行状态，以及名为 `report` 的文件制品记录和实际文件，而不只看“已触发”提示。

这个脚本没有使用仓库地址，因此即使成功，也不能证明仓库认证、默认分支、源码构建或镜像发布成功。它只用于解释阶段和文件制品的配置方式。

## 提交并检查本次运行

1. 在应用流水线中点击“运行”，确认本次分支或标签；不要把标签名视为不可变提交标识。
2. 提交后进入本次运行记录。“流水线已触发”只表示请求受理，仍需等待执行并检查结果。
3. 检查执行配置中的流水线版本、快照、仓库 ref 和变量快照，查看阶段依赖、各阶段状态、退出码、错误和日志。
4. 再查看本次运行的制品及版本关联，确认输出是否齐全。当前流水线或模板页面不能替代历史快照作为本次执行依据。

仅为 CI 准备环境时，保存项目环境后可从初始化返回流水线，不强制先创建和部署网关；SSH 的凭据、主机指纹及执行支持仍是实际前提。

同一仓库有活跃运行时，新的运行可能被拒绝，先确认正在执行的任务。排队后若环境目标或 SSH 凭据绑定发生变化，旧任务会被拒绝而不是改到本机执行；核对新环境后再决定是否重试。

## 取消与重试不是回滚和重放

- “取消”用于等待或运行中的任务。取消后检查终态及执行侧资源，不假定已经完成的脚本写入、镜像推送或外部操作会自动撤销。
- “重试”创建新的运行并关联原记录，不会把原记录改回运行中。它使用当前流水线和执行环境，复用原运行中可用的非系统变量值，并重新校验。
- 因此重试不是原快照的逐字重放，也不保证取到同一提交、使用相同镜像或产生相同结果。重试前核对当前定义、ref、来源版本和目标，特别是会写入外部系统的阶段。
- 删除运行仅适用于已结束的记录，并涉及历史记录及运行文件；保留故障证据和所需产物后再安排清理，不把删除记录当作撤销构建结果。

## 三种制品分别说明什么

| 收集器 | 收集内容 | 需要额外确认 |
| --- | --- | --- |
| `file` | 本次制品目录中已生成文件的位置 | 文件未生成时当前实现可能警告并跳过；运行成功也要核对期望文件，不能只看状态 |
| `command` | 阶段后收集命令的输出，格式为 `text` 或 `git_object_id` | 命令本身会执行；Git 对象格式要求输出为 40 或 64 位十六进制，不要带额外说明或秘密 |
| `docker_image` | 执行侧 Docker 中可检查的镜像引用及本地镜像 SHA256 | 登记不会替你构建或推送镜像，本地镜像 SHA256 也不等于远程仓库已经发布的证明 |

从运行记录或“制品”页面进入详情，核对来源仓库、流水线、阶段、运行编号，以及相应的位置、值、镜像和源码信息。不要把文件位置当作公共下载链接，也不要将制品记录当作远程镜像可拉取的证据。

## 让镜像制品形成应用版本

需要把 CI 输出汇入业务应用时，在复用模板时准备以下关系：

1. 选择本项目业务应用及来源版本策略。`latest` 在创建运行时选择当时最新版本，`fixed` 使用指定版本；两者都不是“只选最新已发布版本”的承诺。
2. 为每个 Docker 镜像制品指定来源版本中存在的组件，例如将 API 镜像映射到 `api`。同一组件只能由一个镜像制品映射，绑定应用时不能遗漏镜像制品的组件关系。
3. 在产出镜像的阶段依赖链上，安排恰好一个 `command` / `git_object_id` 制品，记录真实取到的源码提交。缺少来源、存在多个候选或输出格式错误都会影响校验和收集。
4. 脚本先完成实际镜像构建，确保声明的镜像引用能在执行侧检查；跨主机部署需要的推送及可拉取性另外确认。
5. 全部阶段和绑定制品收集成功后，一次运行将映射的镜像汇入一个新的未发布应用版本。查看制品详情的来源版本、生成版本和组件链接，再到应用版本页核对。

构建失败、缺少绑定制品或没有组件映射时，不应期待生成版本。即使版本已经生成，也不会自动修改服务绑定或部署容器；继续按[应用、版本与服务](./applications-services.md)核对配置并执行部署。

## 遇到失败时

| 症状 | 优先核对 |
| --- | --- |
| 没有运行入口 | 当前是否为不可直接运行的模板，先复用为应用流水线 |
| 提示缺少变量或依赖错误 | 当前仓库 / 流水线配置、阶段作用域及依赖图，而非反复触发 |
| 取源码失败 | [仓库与凭据的实际认证限制](./repositories-credentials.md)、ref、执行侧网络和脚本 |
| 阶段退出非零 | 本次阶段日志、执行镜像中的工具和脚本工作目录 |
| 脚本成功但阶段或运行最终失败 | 制品命令、本地镜像检查、源码提交格式以及版本派生是否失败 |
| 运行成功但没有期望制品 | 是否声明且实际生成了输出，文件制品是否被跳过；不要据此推断镜像已上传 |
| 环境变化后任务、日志或文件不可用 | 核对原运行的目标快照和当前环境，不通过切回本机绕过目标校验 |

保留运行编号、快照、失败阶段和脱敏错误，先识别配置、执行、制品收集还是版本派生失败，再决定调整或重试。不要把认证环境、令牌或敏感命令输出贴入公开反馈。
