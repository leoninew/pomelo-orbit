# 用户、权限与访问令牌

本文说明怎样管理实例用户、分配系统角色、维护项目成员，以及管理自己的自动化访问令牌。项目和执行环境的关系见[核心概念](../concepts/core-model.md)；环境配置见[项目与执行环境](./projects-environments.md)。

## 开始前

- 已有可用的 Pomelo Orbit 实例并已登录。账号管理需要相应的系统权限；项目操作还需属于该项目，不能只根据角色名称判断。
- 明确要调整的是系统权限、项目访问还是某个自动化客户端的身份。变更共享角色或移除成员前，保留另一位有相应权限的维护者及可信恢复通道。
- 使用受信任的设备管理密码和令牌，不将真实值放入仓库、聊天、问题反馈、截图或公开日志。

本指南适用于 `develop` 分支，以已有登录账号为前提，不提供初始账号或忘记密码恢复步骤。操作前保留另一位维护者及可信恢复通道，避免失去管理入口。

## 先区分身份与授权

| 对象 | 决定什么 | 不代表什么 |
| --- | --- | --- |
| 用户 | 实例中的账号、登录身份与启用状态 | 创建账号不自动分配角色或加入项目 |
| 系统角色 | 一组实例级权限码；多个角色的权限取并集 | 角色叫“管理员”不自动获得所有权限或访问所有项目 |
| 项目成员 | 用户能否访问该项目及受成员检查的资源 | 当前没有另设项目只读、操作员或所有者角色 |
| 浏览器登录令牌（JWT） | 当前 Web / 普通 HTTP API 的登录身份 | 不是个人 MCP 访问令牌，也不是 Git 凭据 |
| 个人访问令牌（PAT） | 本地 stdio MCP 与当前本地 CLI 认证的用户身份 | 没有每令牌只读权限或固定项目范围，名称也不产生限制 |

仓库令牌、环境 SSH 私钥和 Cloudflare Token 是访问外部资源的凭据，不能用个人 PAT 替代。具体区别见[仓库与仓库凭据](./repositories-credentials.md)及[网关、DNS 与路由](./gateway-dns-routes.md)。

## 确认所需系统权限

“系统管理”中的菜单和编辑入口会按权限显示；后端仍会独立授权，看到按钮不保证提交成功。

| 操作 | 当前权限要求 |
| --- | --- |
| 查看用户列表与详情 | `user:read` |
| 创建、编辑、启停或删除用户 | `user:write`；从页面完成操作通常还需 `user:read` |
| 查看角色和权限目录 | `role:read` |
| 创建、修改或删除角色 | `role:write`；从页面完成操作还需 `role:read` |
| 给用户分配角色 | 后端同时要求 `user:write`、`role:write`；页面还需 `user:read`、`role:read` |
| 查看登录历史 | `login:read` |
| 查看 / 修改系统设置 | 分别为 `setting:read` / `setting:write` |
| 查看部署对话历史 | `dialogue:read`，并属于请求项目 |
| 发送、继续或删除部署对话 | `dialogue:write`，并属于请求项目；完整页面通常还需 `dialogue:read` |
| 管理自己的访问令牌 | 启用账号的有效 Web 登录，不要求用户或角色管理权限 |

角色权限目录中的上述九项权限与项目成员关系分别管理。不要从角色名称推导“只读流水线”或“仅允许部署某个服务”等未提供的细粒度权限；共享仓库、模板及外部 DNS 也不会因为切换项目就变成项目私有资源。

授予 `setting:read` 前注意：系统设置响应包含敏感原值，页面遮罩不是只读脱敏权限；`setting:write` 还可改变下一次启动配置。保存 / 重置、重启及主密钥影响见[配置与密钥](../operations/configuration.md)，不要通过换主密钥代替撤销个人 PAT。

部署对话的读写权限不等于只读工具策略；历史按项目共享，发送可能直接执行业务。配置前提、共享和执行限制见[部署对话](./deployment-dialogue.md)，不要把个人 PAT 的外部 MCP 认证套入应用内对话。

## 创建和维护用户

1. 打开“系统管理 → 用户”，点击创建用户，填写唯一用户名、有效且唯一的邮箱和密码。
2. 当前密码长度校验为 6–36 字节；这是输入约束，不是强密码建议。选择足够强的密码并通过安全通道交付，不在文档或工单中共享。
3. 创建后检查邮箱、账号状态和角色。新账号默认启用，但没有自动授予系统角色或项目成员资格；按实际职责继续配置。
4. 告知使用者：密码登录使用**邮箱**，不是用户名。新建账号使用创建时设置的密码；全新实例的首登另见[自托管安装](../getting-started/installation.md)，不要将初始化凭据用于已有账号或恢复实例。

编辑已有用户时，密码留空表示不修改。需要调整邮箱或用户名时，先核对是否影响使用者登录和识别；重复值会被拒绝。

### 修改与重置密码

- 修改自己的密码：从用户菜单进入“修改密码”，填写旧密码、新密码及确认值；当前流程要求旧密码，不是忘记密码恢复入口。
- 从用户管理重置密码：需要 `user:write`。若目标是另一位拥有 `role:write` 的用户，操作者还必须有 `role:write`；否则重置会被拒绝。拥有 `user:write` 的操作者可重置普通用户密码，这不是仅有“管理员”名称才能执行的操作。
- 当前改密和 Web 退出登录不会使已签发的 JWT 或 PAT 在服务端统一失效。不要把这两种操作当作泄露凭据的吊销措施；个人 PAT 需显式撤销，账号禁用只能阻止禁用期间的后续认证。

### 禁用与删除

禁用后，后续 Web 登录认证和 PAT 认证会拒绝该账号；它不删除账号或成员关系，也不停止已受理的流水线、部署或运行容器。重新启用后，仍有效且未撤销的令牌可能继续可用，禁用不等于永久吊销。

删除用户会移除其角色关联、项目成员关系和账号；已有登录历史保留，不等于清空审计或撤销曾执行的业务操作。当前不能禁用或删除正在执行管理操作的账号自身，但不要据此推断修改角色、移除成员也有“保留最后一位管理员”的保护。

## 创建角色并分配权限

1. 打开“系统管理 → 角色”，创建角色并填写编码、名称及可选说明。编码只使用字母、数字、`_`、`-`；编码和名称均需唯一。
2. 进入角色详情，编辑权限并选择必要的权限码。当前创建界面提交的是空权限列表，**仅创建角色不授予任何权限**。
3. 保存后重新核对权限集合。编辑提交的是完整集合，取消选中会撤销该权限，不是只追加新项。
4. 进入目标用户详情，编辑角色，选择需要保留的完整角色集合并保存；清空选择会移除该用户的全部角色。
5. 重新查看用户角色及允许的操作。后端权限检查读取当前数据；若菜单仍显示旧状态，可刷新页面重新获取身份信息，不能把旧菜单当作仍有权限的证明。

修改共享角色会影响全部持有该角色的用户。删除角色前需解除所有用户对它的分配，否则删除会被拒绝。避免直接用自己的唯一管理角色试验撤权；当前没有自动保证保留最后一位可管理用户的机制。

## 管理项目成员

项目列表按当前用户的成员关系提供，创建者会成为新项目的初始成员。系统角色不会自动绕过项目访问检查。

1. 打开“系统管理 → 项目”，进入你所属项目的详情并查看成员。
2. 添加已存在的启用用户；这一步不会新建账号或发送邀请邮件。当前成员管理接口校验项目成员身份，没有额外的项目所有者角色或 `role:write` 要求。
3. 页面同时读取项目成员和用户候选，因此从当前界面管理成员还需要 `user:read`。用户候选只来自读取的前 100 个用户，并过滤禁用账号与已加入成员；未出现在候选中不证明账号不存在。
4. 保存后重新查看成员列表。移除前确认仍保留需要的成员，尤其不要依赖系统阻止移除自己或最后一位成员。

成员被移除后，后续受成员关系检查的项目访问会被拒绝；这不会禁用其实例账号、移除系统角色、撤销所有个人令牌或停止已提交的业务。该用户仍可能访问其他所属项目及获准访问的共享资源。

成员区加载失败时，应分别检查项目成员身份和 `user:read`，不要仅增加 `role:write` 试图解决。若用户因候选范围未显示，由有权限的维护者核对账号及现有接口能力，不盲目重复创建用户。

## 管理自己的访问令牌

### 创建、查看与保存

1. 打开“系统管理 → 访问令牌”。这里只管理当前登录用户的个人令牌，不是所有用户令牌的管理列表。
2. 点击创建，填写便于识别用途的名称，主动选择有效期。当前界面提供永不过期、30 天、90 天和 365 天，默认是**永不过期**；按用途选择尽可能短的有效期，不依赖默认值替你限制时长。
3. 创建后核对名称和到期时间，再按需要显示或复制令牌，存入可信的凭据管理工具。按客户端分开创建便于独立撤销，但不产生额外的权限隔离。
4. 配置使用者时，使用完整的个人令牌，不是记录 ID、浏览器 JWT、Git 密码或环境私钥。本文不提供真实令牌或完整客户端启动配置。

**当前令牌不是只展示一次。** 系统保存哈希及可恢复的加密值，所有者以后仍可在列表中显示和复制。保护 Web 会话、实例数据及加密密钥同样重要；页面遮罩不表示秘密不可恢复。

旧记录若没有可恢复值，页面显示 `-`，不能从记录 ID 或哈希还原令牌，应按轮换流程替换。若整个列表加载失败，不要通过随意更换实例加密密钥来修复，以免其他已存秘密也无法读取。

### 理解自动化权限边界

- PAT 代表其所有者，操作仍受该用户当前权限、项目成员关系及具体入口的检查约束。令牌名称写“只读”不会限制写入，选择某个项目也不是永久绑定该令牌。
- 当前普通 HTTP API 使用 Web JWT，不能直接把个人 PAT 当作通用 Bearer 凭据。这里的 MCP 与 CLI 是本地入口，不是通过 Web HTTP API 代理执行的远程客户端。
- stdio MCP 会在每次 `tools/call` 前重新校验配置的 PAT；成功握手或列出工具不证明令牌有效。撤销、到期或禁用所有者会阻止后续工具调用，不取消已经受理的操作。
- 当前本地 CLI 在打开应用服务时认证 PAT，不能据此承诺运行中的长命令会随撤销即时中断；本地转发进程管理等入口也不应概括成每条命令都需 PAT。

### 撤销与轮换

在自己的令牌列表选择撤销并确认，随后刷新核对。撤销会删除该令牌，后续使用它认证将失败，不能通过重新启用账号恢复已撤销令牌。

正常轮换顺序是：创建替代令牌 → 通过安全通道更新使用它的客户端 → 在授权范围验证所需操作 → 撤销旧令牌。怀疑泄露时优先撤销受影响令牌并评估账号及已执行操作，不为维持旧客户端可用而继续暴露秘密。撤销不负责停止正在执行的部署、容器或转发进程，必要的停止操作需要另外判断和执行。

配置本地客户端时，继续阅读[MCP 与 CLI](../reference/mcp-cli.md)，核对配置目录、实例数据和项目选择，并按本节的权限与令牌规则管理客户端身份。

## 检查结果与常见问题

| 现象 | 先检查什么 |
| --- | --- |
| 创建用户成功，但没有项目或管理菜单 | 分别检查成员关系和系统角色，不重复创建账号 |
| 用户角色编辑可打开，保存却被拒绝 | 后端同时要求 `user:write`、`role:write`；读取权限或菜单可见不代替写权限 |
| 角色删不掉 | 是否仍分配给用户；先评估撤权影响再解除关联 |
| 成员区加载失败或候选缺失 | 当前成员身份、`user:read`、账号启用状态、已加入关系及首批 100 个候选限制 |
| Web 请求提示未认证或无权限 | 区分 JWT / 账号状态与系统权限；不要用 PAT 替换 Web 登录凭据 |
| MCP 能列工具但调用失败 | PAT 的完整值、到期 / 撤销、所有者状态，以及本次操作的项目和权限 |
| 已撤销令牌，先前任务仍在执行 | 撤销阻止后续认证，不负责取消已受理工作；另查任务或进程的当前状态 |

反馈时保留时间、入口、脱敏错误、账号及项目标识，不附带密码、令牌或完整认证头。权限变更后分别核对管理入口和项目访问；怀疑泄露时还需评估已执行操作，不只更改页面配置。
