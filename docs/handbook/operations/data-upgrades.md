# 数据保留与升级

本文面向实例维护者，帮助你识别需要保留的数据，安排备份、恢复演练和版本升级。**平台数据库、业务容器数据和外部资源是三套不同的恢复对象**；只备份其中一项不能恢复完整实例。

本指南适用于 `develop` 分支。具体恢复工具取决于你的数据库、操作系统和存储方案；先在隔离环境演练，不在唯一的生产数据副本上试验升级或降级。

## 先列清楚要保留什么

| 内容 | 保存什么 | 去哪里确认实际位置 |
| --- | --- | --- |
| 平台数据库 | 用户、权限、项目、环境、应用、服务、运行记录、队列及部分加密凭据等 | 当前 `database.url`；可能是 SQLite、MySQL 或 PostgreSQL，不一定与程序同机 |
| 启动配置与主密钥 | 数据库地址、JWT / 凭据解密主密钥、外部服务配置和 profile | 启动工作目录、所选 dotenv、进程管理环境、`configs/` 和 `overwrite.env` |
| 设置恢复文件 | 应用覆盖的锁、中断写入恢复记录 | **启动工作目录**下的 `data/config/`，不随 `orbit.root` 自动迁移 |
| 平台及执行日志 | 排障和审计所需的运行、阶段、部署输出 | `logging.file`、`logging.deployment_root`，以及项目工作区中的运行日志 |
| CI 工作区和文件制品 | 工作副本、运行文件、阶段日志和已收集文件 | 项目环境工作目录的 `pipeline/` 下；不要把数据库中的制品记录当作文件备份 |
| CD 部署目录 | 生成的 Compose、受管文件、目录挂载及相关配置 | 每个服务实际部署目录，可能在本机，也可能在 SSH 目标上 |
| Docker 卷和外部挂载 | 业务数据库、上传文件、缓存之外的持久数据等 | 实际容器挂载、Docker daemon 和外部存储；命名卷不等于部署目录中的普通子目录 |
| 网关与入口材料 | 路由发布文件、证书私钥、ACME 状态及恢复材料 | 网关实际挂载与部署目录，不能只备份网关的数据库定义 |
| 外部资源 | DNS 记录、镜像仓库内容及外部服务的状态 | 对应供应商或受管系统；Orbit 数据库恢复不会回滚它们 |

按[自托管安装](../getting-started/installation.md)的 Docker 示例部署时，宿主机的 `data/`、`logs/`、`.env`、`overwrite.env` 和 `compose.yaml` 是首批需要保留的内容；镜像版本 / ID 也要记录。该示例放在 `data/` 外的额外挂载、Docker 命名卷和 SSH 目标不在这个目录的备份范围内。

原生程序包的相对 SQLite 地址 `sqlite:///data/db/pomelo-orbit.db` 指启动工作目录下的文件。换一个目录启动可能得到另一份空数据库；不要因看不到旧项目就断定数据已被删除。绝对路径、容器挂载和外部数据库应按实际配置核对，不能全部按 `orbit.root` 推算。

## 保留策略与权限

1. 记录实例版本 / 提交、数据库类型、程序工作目录、profile、挂载映射和执行目标；记录秘密的保管位置，不把明文秘密抄入操作清单。
2. 为数据库、业务数据及日志分别确定允许丢失的时间范围、保留周期和恢复负责人。制品若不能重新构建，应按交付数据保留，而不是当缓存清理。
3. 备份保存在与源数据故障隔离的位置，限制读取权限并按要求加密。数据库、Compose、恢复记录和日志都可能含秘密，不能上传到公开 Issue 或 Git。
4. 保留与数据库匹配的主密钥及可用旧程序 / 镜像。没有原密钥，即使能恢复用户和服务记录，也可能无法解密仓库凭据、SSH 私钥和令牌原值。

日志轮转只控制部分平台日志，不是统一的数据保留策略；不要据此推断制品、部署目录、数据库或容器卷会自动清理。

## 安排一次一致的备份

### 1. 停止新写入并确认在途任务

安排维护窗口，通知用户暂停流水线、部署、配置、对话和自动化写入。检查已受理任务，等待它们结束或按业务流程处置，记录仍未完成的操作。

然后按实际进程管理方式停止所有访问这套平台数据的 Web、独立 Worker、MCP 和 CLI 会话，防止配置写入或任务继续受理。**关闭浏览器不算停写，停止 Orbit 也不保证远端命令已经结束。** 还需检查目标主机上的在途操作。

安装包启动器可能在短暂等待后强制结束进程；不要把运行 `stop` 当作任务已安全排空。停机前后分别核对进程和任务状态。业务容器通常仍会运行：若需要备份它们的数据，必须另行安排该业务的停写或数据库一致性快照。

### 2. 按存储类型创建备份

| 存储类型 | 操作要求 |
| --- | --- |
| SQLite | 当前使用 WAL。选择全部连接关闭后的离线备份，或由维护者使用 SQLite 支持的一致性备份方式；不要在运行中仅复制主 `.db` 文件，也不要手工删 `-wal` / `-shm` 来“整理” |
| MySQL / PostgreSQL | 使用数据库原生且与版本相容的备份 / 恢复工具或受控快照，确认事务一致性、必要对象及恢复权限；不要直接复制正在运行的数据库数据目录 |
| 配置与恢复目录 | 在相关进程停写后，一并保留启动配置、秘密、`overwrite.env` 和 `data/config/`；不手工删除锁或未完成写入记录 |
| 业务卷与挂载目录 | 遵循对应业务的备份流程，确保数据写入一致；复制 Compose 只能恢复声明，不能恢复卷里的内容 |
| 远端工作区与网关材料 | 在实际目标上备份所需文件及权限；本机安装目录备份不会包含 SSH 主机上的数据 |

记录备份时间、所用版本、数据范围和未包含项，确认备份文件可读且完整。单次“文件复制成功”不等于恢复可用。

### 3. 先在隔离环境恢复演练

1. 准备独立数据库、目录、Docker daemon 和网络，使用备份副本，不让演练实例连接生产数据目录或生产 Docker socket。
2. **启动前隔离生产执行目标和外部服务访问。** 恢复的数据仍含队列、SSH 凭据、DNS / 模型配置等；`serve` 会自动启动 Worker，并非只读查看模式。先由维护者核对恢复副本的任务和目标，不能靠“我不点击部署”防止动作发生。
3. 恢复匹配的程序版本、数据、主密钥、启动配置和所需文件，保留目录映射及权限。需要重新映射目标时，只修改演练副本，不覆盖生产环境。
4. 在隔离条件成立后启动，检查迁移日志、登录、项目 / 应用 / 服务记录、必要的凭据解密及文件制品。验证时不要显示或外发秘密原值。
5. 选择一个专用无状态测试服务检查执行和访问，记录恢复耗时及缺失内容；有状态业务需用其自身的查询 / 一致性检查验收，不能仅看容器启动。

恢复演练失败时先修正备份方案，再安排正式升级。保留原备份不变，避免把演练产生的新写入当成原始恢复点。

## 升级平台实例

平台升级与业务服务版本更新分开进行。平台启动会自动运行数据库向上迁移；**替换程序后再启动，本身就可能修改数据库**。

1. **确认目标版本。** 阅读目标版本变更与迁移要求，记录当前和目标版本；没有已发布包时，固定源码提交构建新的独立镜像标签，不只记录 `latest`。
2. **准备回退材料。** 保留旧程序 / 镜像、旧启动配置与一致备份。先完成隔离恢复和升级演练，确认预计停机窗口及接受的恢复点。
3. **停止写入与执行进程。** 按前面的维护步骤排空或处置任务，停止旧 Web / Worker / 本地自动化入口；不要让旧版与新版同时对同一数据库执行任务或迁移。
4. **部署新程序，保留原数据。** Docker 安装只替换目标镜像引用，保持已确认的挂载、工作目录及主密钥；不执行带删卷的清理。程序包应整体保留相匹配的二进制和 `static/`，比较新旧配置，不把新 `.env.release` 覆盖到旧秘密上。
5. **核对配置再启动。** 保留实际需要的覆盖，并检查新版本的类型和组合约束；`overwrite.env` 优先级最高，新模板默认值不一定生效。只启动受控的目标版本进程，观察迁移完成和运行日志，再恢复需要的其他入口。
6. **逐层验收。** 检查登录与权限、项目 / 环境 / 应用 / 服务、设置是否实际生效、执行日志和必要制品，最后在隔离业务上检查一次运行及访问；核对外部资源是否有意外变化。
7. **恢复使用。** 确认结果后开放入口和自动化，观察新任务与错误日志。保留恢复点至约定观察期结束，不因首页能打开就立即删除备份。

如果换了原生程序所在目录，必须显式保留或迁移相对数据库、日志和覆盖文件的位置。复制新版二进制到另一个目录后直接启动，既不迁移旧数据，也不保证使用同一实例。

## 升级失败与恢复边界

| 情况 | 应怎样处理 |
| --- | --- |
| 启动前发现配置无效 | 保留原进程和数据的已知状态，核对字段及覆盖；不要为通过校验生成新主密钥 |
| 迁移报错或数据库 dirty | 停止其他写入，保全错误、版本与数据，由维护者确定修复或恢复方案；不手工清除标记、跳过迁移或修改已执行的迁移 |
| 新版本迁移完成但业务异常 | 不直接把旧二进制指向已升级数据库；先判断是否兼容，必要时按演练方案恢复旧版、匹配配置和一致备份 |
| 需要恢复升级前备份 | 明确会丢失恢复点之后的写入，协调平台与业务数据时间点及外部操作，再恢复；不是“撤销最后一次按钮操作” |
| 数据库已恢复但容器 / DNS 仍是新状态 | 对照恢复前清单核对真实资源，安排受控修复；数据库恢复不会自动回滚容器、镜像推送、DNS 或外部系统 |

当前程序的普通启动入口不是数据库降级工具，系统设置也不提供通用的主密钥重加密或一键恢复。不要从存在历史迁移文件推断任何跨版本降级都安全。具体故障检查见[故障定位](./troubleshooting.md)。

## 日常变更中最容易丢失数据的地方

- 修改环境主机或工作目录不会搬迁旧容器、数据和制品；先规划迁移，再改变业务指向。
- 修改服务部署目录会改变相对挂载的位置。新目录空数据不等于旧数据消失，也不能用复制几份配置代替业务迁移。
- “停止并删除 volumes”是数据删除选择；没有经过确认的清理方案时不要勾选。删除服务记录不证明运行资源已清理。
- 给有状态服务修改初始化密码并重新部署，不会自动修改已经初始化的数据卷内的账号密码；需要业务自身的凭据轮换流程，不靠删卷解决认证错误。
- 换 JWT 主密钥会影响既有密文和登录，不是统一撤销 PAT。密钥用途与变更风险见[配置与密钥](./configuration.md)。

业务版本及停止操作见[应用、版本与服务](../guides/applications-services.md)；每次操作都应确认当前目标、实际数据归属和恢复入口。
