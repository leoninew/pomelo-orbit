# 应用流水线跟进模板流水线更新
最后修改时间: 2026-09-23 17:19:05

Review status: Draft

Mode: strict

## Background

Template Pipeline 将引入的阶段保存为 `PipelineStageReference` 快照；Application Pipeline 实例化时复制这些引用及变量配置，之后两者独立演进。现有“更新至模板”针对单个阶段的**阶段模板版本**，没有将已创建 Application Pipeline 跟进其**来源 Template Pipeline 版本**的操作。

2026-09-23 的实际案例：模板流水线 `01M2SS37JDME33162ZJV500MWB` 删除并重新引入 `docker build` 后从 v13 变为 v15，新引用包含 `{{ repository_dockerfile | default: "Dockerfile" }}`；应用流水线 `01M36Q2KYZ91J8CZ9BYA4HDCGY` 仍记录来源 v13，旧阶段脚本仍为 `{{ repository_dockerfile }}`。两边关联的独立阶段模板均为 v3，按阶段模板版本判断不会提示可更新。此处是两层快照的差异，并非单纯的变量取值问题。

既有约定是模板或阶段模板后续变更不自动改变已创建的应用流水线；本任务讨论是否需要在保持可控性的前提下提供**跨 Template Pipeline 版本**的跟进能力，不预设具体交互或合并算法。

## Goal

1. 让用户能辨认来源 Template Pipeline 的新版本与当前 Application Pipeline 来源版本的差异，避免与“更新阶段模板”混淆。
2. 探索用户如何选择是否采纳模板流水线的阶段编排、脚本、制品及变量配置变更，同时保护应用流水线的私有配置。
3. 明确更新后版本记录、运行快照和已有 Run 的边界，使更新结果可理解、可验证。

## Non-goal

- 本意图草稿不实施代码、数据库写入或现有流水线修复。
- 不把“模板版本数字变化”直接视为应用阶段已更新，也不回写历史 Run/Snapshot。
- 暂不将独立阶段模板的“更新至模板”操作等同于整条模板流水线的更新。

## User scenarios

1. 模板流水线调整阶段引用（例如删除并重新引入阶段，脚本增加 Liquid `default`）后，用户在应用流水线看到来源版本差异，决定是否更新。
2. 应用流水线已有私有阶段名称、DAG、阶段变量覆盖、制品 Component 映射或 Version 策略时，用户需要知道模板更新会保留、替换还是要求重新指定哪些内容。
3. 用户拒绝或暂缓更新时，现有应用流水线继续按原阶段脚本运行；新实例化的流水线使用最新模板引用。

## Acceptance（候选，待确认范围）

- 能区分 Template Pipeline 版本变化与独立阶段模板版本变化，并准确展示当前实例使用的来源版本。
- 用户在采纳变更前能了解受影响的阶段、变量与绑定；不能悄然丢失应用流水线的私有配置。
- 若提供更新操作，成功后来源版本及实际阶段内容一致；失败不留下部分更新的可运行配置。既有 Run/Snapshot 保持不可变。

## Open questions

1. 更新是完全显式的整条流水线操作，还是支持按阶段选择／自动跟进？“仅提示有更新”是否已满足首期需求？
2. 对新增、移除、重排的阶段及变化的依赖，如何匹配重建的引用 ID 与应用阶段 ID？已有应用私有改动与模板变更冲突时谁优先？
3. 模板变量配置的阶段作用域如何映射；制品变更导致 Component 绑定失效时是阻止更新，还是允许用户交互补齐？
4. 是否需要差异预览、一次性确认、并发版本校验与回退能力？应用流水线的 `source_template_version` 在部分更新时如何定义？

## Decisions

- 只确认“记录并讨论应用流水线跟进模板流水线版本”的问题范围；尚未选择同步策略、操作粒度或 UI 流程。
- 因涉及编排、变量和制品绑定的安全演进，采用严格模式 / strict，停留在意图 / Intent 草稿。

## Risks / assumptions

- 现有阶段模板版本相同也可能存在模板流水线引用快照差异，不能复用单阶段版本比较代替整条流水线差异判断。
- 模板引用更新不会自动进入已实例化应用流水线；若要支持同步，应先处理阶段身份、依赖、变量作用域和制品 Component 映射，不能只更新来源版本字段。
- 用户尚未决定目标交互和冲突处理；以上验收条目均为讨论起点，不能直接当作实施授权。
