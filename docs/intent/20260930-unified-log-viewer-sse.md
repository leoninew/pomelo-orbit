# CI/CD 日志功能、样式与组件统一及 SSE 流式传递
最后修改时间: 2026-09-30 14:50:20

Review status: Accepted

Flow mode: standard

## Background

项目已经有多处日志能力，完成度体现在不同层面：CI/CD 操作日志已有持久化、增量读取和任务终态判断；运行时容器日志已有共享抽屉、请求取消和刷新竞态控制。与此同时，部分页面仍自行拼装日志区域，公共操作不完整，容器输出依赖重复快照读取。统一工作需要吸收这些已有能力、补齐各入口的功能差距，并统一样式与组件。

用户已确认采用 Fetch + SSE 作为 Web 日志的流式传输方式；所有范围内日志都应在产生过程中持续读取，部署详情的容器日志也应在部署进行中订阅，不等待任务完成。用户同时要求移除日志控件中的复制能力。本意图记录本次代码评估结果与功能范围，具体接口、组件划分和实施步骤在 Plan 阶段确定。

### 现有 Web 日志入口

| 场景 | 展示实现 | 获取方式与生命周期 | 已有能力与缺口 |
| --- | --- | --- | --- |
| CI 阶段日志 | `web/src/views/pipeline_run/PipelineRunDetail.vue` 内自建 `AppDrawer` 与只读 Monaco | 每 1.5 秒按字节 offset 增量读取；Stage `is_complete` 后停止 | 已有历史读取、追加、终态判断和 Abort；展示与状态处理独立，缺少统一操作；页级 Run 刷新与阶段日志轮询相互独立 |
| CD 操作日志，包含部署、重启、停止 | `web/src/views/deployment/DeploymentDetail.vue` 操作日志 tab 内自建只读 Monaco | 随详情每 2 秒按 offset 增量读取；Deployment 终态后停止 | 已有追加、终态判断、generation 与 Abort；加载、空态、错误与滚动重复实现 |
| CD 部署记录中的容器日志 | `DeploymentDetail.vue` 的 `ContainerLogView` | 当前前端等待操作结束后读取快照；停止操作不展示容器日志 | 后端优先读取操作开始以来的输出，失败时取 tail；与持续运行的容器日志在时间范围和订阅时机上存在业务差异 |
| Service 组件日志 | `ServiceDetail.vue` -> `RuntimeContainerLogsDrawer` -> `ContainerLogView` | 每 2 秒取最近 200 行并整体替换；可手动暂停、刷新 | 共享组件、空态、重试、请求取消与竞态处理较完整；高输出量下快照间可能遗漏日志，关闭后清空内容 |
| Gateway 日志 | `GatewayDetail.vue` -> 同一共享日志抽屉 | 同上；特定部署关联场景还会检查 Deployment 是否结束 | 复用已有组件；日志功能与传输能力仍受快照方式限制 |
| Route 页日志 | `RouteDetail.vue` -> 同一共享日志抽屉 | 读取该 Route 关联 Gateway 的容器日志 | 属于 Gateway 日志的另一个入口，不是独立 Route 日志源 |

### 后端日志来源与读取实现

| 来源 | 存储或生产方式 | 当前应用服务与适配器 |
| --- | --- | --- |
| CI 阶段日志 | 执行环境 `<workspace_root>/pipeline/runs/<run-id>/stages/<stage-run-id>.log`；stdout/stderr 写入文件 | `PipelineStageLog` 位于 `internal/application/pipeline_run/usecase/service.go`；local 使用 `internal/infrastructure/storage/local/executionlog/store.go`；SSH 使用 `internal/infrastructure/runner/ssh/pipeline.go` 中的 SFTP 读取 |
| CD 操作日志 | 控制面 `logging.deployment_root/logs/<service-code>/<deployment-id>.log`；包含本机或 SSH 执行输出 | `DeploymentLog` 位于 `internal/application/deployment/usecase/service.go`；使用 `executionlog.DeploymentStore` |
| 容器日志 | 在 Project Environment 上执行 `docker compose logs --tail` 或 `--since`；目前没有 `--follow` | `ApplicationLogs` 位于 `internal/application/deployment/usecase/runtime_query.go`；`DeploymentContainerLog` 位于 `internal/application/deployment/usecase/service.go`；local/SSH runtime 的 `Query` 等待命令结束并返回字符串 |

其他日志实现：

- MCP 的 `orbit_deployment_logs`、`runtime_compose_logs` 复用上述应用服务，当前提供按需读取，不是 Web 流式订阅。
- 控制面 `slog`、HTTP 请求日志与文件轮转位于 `internal/bootstrap/logger.go`、`internal/api/http/middleware/logging.go`，当前没有对应的 Web 日志阅读页面。
- SSH 宿主机终端使用 WebSocket + xterm，包含交互输入与 PTY；它是独立的终端能力。
- 部署对话已有 Fetch + SSE：前端 `web/src/api/dialogue/dialogue.ts`，服务端 `internal/api/http/handler/dialogue/dialogue.go`。Bearer 认证、事件编码、增量解码、错误反馈和禁止代理缓冲的处理可作为参考，但现有逻辑仍绑定对话事件与请求时限。

### 评估结论

1. **控件统一具备基础，工作量中等。** 可以以 `ContainerLogView`、`RuntimeContainerLogsDrawer`、`MonacoEditor`、`AppDrawer` 为参考，把各入口的日志通用功能收敛到共享实现，并补齐 CI/CD 的独立页面实现。
2. **CI/CD 操作日志流式化工作量中等。** 持久化日志和字节游标可支撑历史回放及断线续读；需要解决分块读取、订阅结束、最后输出的读取与 SSH 持续连接。
3. **容器日志流式化工作量较高。** 当前重复读取快照，缺少持续输出适配；需要在 local/SSH 运行时支持持续读取，不能仅将 `--follow` 加到等待结束、缓存完整结果的 `Query` 中。
4. **Fetch + SSE 适合单向日志推送。** 可以沿用 Bearer 认证，已有项目实现可参考。WebSocket 也可实现日志流，但本任务采用用户明确选择的 Fetch + SSE。
5. **展示状态需要独立于日志正文。** 目前多个入口仅在无日志时显示加载或错误，已有内容可能遮住读取失败；任务完成、订阅暂停、连接中断、无输出应具有明确区别。
6. **流式化需要同时处理展示成本。** 当前 CI/CD 累积完整字符串并更新 Monaco，文件读取一次返回所有剩余内容；需要有界分块、批量追加及展示缓存策略。

## Goal

1. 覆盖 CI 阶段、CD 操作、部署记录容器日志，以及 Service、Gateway、Route 的运行时容器日志入口，统一日志功能基线。
2. 吸收现有实现中成熟的历史读取、请求取消、竞态控制、资源定位、Project 授权和终态判断；原始实现补齐相同的通用操作与状态反馈，避免统一后功能退化。
3. 所有范围内 Web 日志统一采用 Fetch + SSE，在任务执行或容器运行过程中持续接收新增输出；打开日志时补读已有输出，不等待操作完成才开始读取。部署详情的容器日志在部署进行中订阅，容器尚未创建时显示等待输出并在可读取后开始传递；已完成任务仍能读取历史日志。支持连接状态、任务结束、错误及重新连接，断线续读能力按日志源的真实能力定义。
4. 统一样式：遵循现有主题、Typography、共享按钮与抽屉规范，统一工具栏、间距、加载/空态/错误展示；状态文字、图标及操作不重复表达相同业务意义。
5. 统一组件：共享日志阅读区域与公共操作，抽屉使用统一外壳；页面内嵌日志和抽屉日志复用同一阅读能力，业务层保留资源和日志来源的差异。
6. 改善持续输出的阅读体验，包括可控制的跟随输出、搜索与错误后的恢复；日志控件不提供复制操作。按下文工程默认方案，暂停只控制滚动跟随，本次不新增导出功能。
7. 日志订阅关闭、页面卸载和 Project/资源切换时正确清理读取连接；仅取消日志读取，不取消 CI/CD 任务或改变容器运行状态。

## Non-goal

- 不建设新的控制面系统日志管理平台，不改造 `slog`、文件轮转或全局 HTTP 日志框架。
- 不将 SSH 交互终端改为 SSE，不把终端输入、PTY 或 xterm 生命周期合并到只读日志组件。
- 不建设集中日志采集、跨资源日志检索、长期日志归档或新的存储/消息队列基础设施。
- 不改变 CI/CD 任务调度、WorkStatus 定义、Environment 的 SSH 用户、受管凭据和 host-key 校验方式。
- 不为展示统一强行消除业务差异，例如 Stage/Deployment 操作日志具有终态，而运行时容器日志不因一次部署任务结束就等价于日志结束。
- 不将部署对话、脚本编辑、Compose 预览、登录历史纳入本次日志阅读组件统一。
- MCP 保持按需日志读取用途，本次不新增 MCP 流式订阅协议。
- 日志控件不提供复制功能或复制操作入口。
- 本次不新增日志下载、导出或服务端全历史搜索。当前日志入口没有统一的导出实现，先完成实时阅读和现有功能统一。

## User scenarios

1. 用户打开未完成 CI 阶段日志，先看到已有输出，再持续看到新增输出；阶段结束后显示完成并保留最后输出。已完成阶段能够读取历史日志。
2. 用户查看 CD 部署、重启或停止的操作日志，使用与 CI 一致的日志控件和公共操作，持续观察执行输出，区分失败原因与日志读取失败。
   用户在部署进行中打开容器日志即可订阅；尚无容器时明确显示等待输出，容器开始输出后立即持续展示，不等待部署结束。停止操作不展示容器日志的现有规则保留。
3. 用户从 Service、Gateway 或 Route 打开容器日志，在相同的工具栏与阅读区域查看持续输出；可阅读历史而不被强制跳回底部。
4. 日志已经显示时连接发生错误，用户仍能看到现有内容，异常通过项目共享 Toast 提示；短暂故障自动恢复，文件日志从已有游标继续读取。
5. 用户暂停滚动跟随后仍接收新增输出，CI/CD 任务继续执行。关闭日志抽屉结束订阅并保留页面内的阅读状态，再次查看同一资源时补读后续日志。
6. 用户切换 Project 或日志目标时，旧订阅释放，旧请求和事件不能追加到新资源视图。

## Common behavior

按常见实时日志查看器的阅读模式、按需订阅和有界缓存原则，结合项目现有实现给出以下工程默认方案。用户已采纳这些建议并要求开始计划，具体参数在 Plan 中落实。

| 能力 | 统一行为 | 业务边界 |
| --- | --- | --- |
| 状态反馈 | 正文始终可见，读取异常统一 Toast；日志控件不承担异常展示，不显示“读取完成” | 连接中断不等于任务失败；暂停跟随不等于断线；无输出与任务未结束可以同时成立 |
| 跟随输出 | 默认查看最新输出；用户上滚或关闭跟随后保留阅读位置，可恢复跟随 | 跟随只控制视口，不停止网络接收 |
| 暂停与继续 | 持续接收输出，暂停仅控制自动跟随；上滚后保持阅读位置，回到底部或主动恢复时继续跟随 | 移除现有“暂停刷新”的接收控制，统一为跟随输出控制，避免制造主动停收后的补读缺口 |
| 搜索 | 所有日志入口提供一致的当前加载内容搜索体验，优先复用 Monaco 能力 | 不增加服务端全历史检索 |
| 功能范围 | 统一现有阅读功能，补齐搜索、可控制跟随和读取错误后的恢复；移除复制，本次不新增导出 | 当前各日志入口没有统一导出能力，导出不是本次流式阅读的必要条件 |
| 抽屉重开 | 保留当前页面内同一资源的内容、游标和阅读位置；关闭时结束订阅，重开后补读；离页或换 Project/目标时清理 | 现有日志关闭就会停止读取，继续沿用按需连接；缓存状态在页面/业务层保留，不要求关闭的抽屉 DOM 常驻 |
| 大日志 | 分块传输与批量追加，限制展示缓存并明确提示截断 | 限制展示缓存不等价于删除持久化文件或扩大 Docker 日志保留承诺 |

已有 `docs/intent/20260811-log-viewer-auto-scroll-refresh-parity.md` 记录了强制滚底的历史决策。本任务改为可控制的跟随输出，以允许持续输出期间阅读历史；用户已采纳该变化，不修改旧过程文档，也不把其历史代码描述作为当前实现依据。

## Practice and project assessment

### 阅读体验与组件

实时日志通常将接收数据与视口跟随分开，允许用户回看历史。项目当前所有日志更新均强制滚底，且已有内容时错误容易被遮住，因此统一后的核心提升是共享状态处理、可控制的跟随和一致的恢复操作。Monaco 已支持主题、行号、查找与长文本显示，继续复用；日志层负责批量追加与缓存边界，避免影响其他脚本编辑页面。

抽屉继续使用项目 `AppDrawer`，内嵌页与抽屉共享阅读区域和紧凑工具栏。连接状态与跟随开关表达不同含义，避免用旋转图标与文字重复展示同一状态。关闭日志视图继续释放网络连接，在当前页面缓存阅读内容和游标；这与现有日志停止读取的行为一致，同时改善重开就丢失内容的问题。

复制按用户要求移除。此前导出为新增提案，现有日志入口没有对应的统一能力；本次收敛到流式阅读、状态处理和组件统一，不新增导出。

### 数据来源与流式生命周期

保留已有日志来源，用统一 SSE 传递增量事件。CI/CD 文件日志沿用字节游标，服务端持续增量读取本地文件或 SSH SFTP，订阅期间复用读取连接；容器日志通过既有 local/SSH runtime 增加持续读取适配，使用 Compose 持续输出。两类源共用传输与展示契约，历史恢复能力仍按来源定义。

打开任务文件日志时从头补读；打开 Service/Gateway/Route 容器日志时沿用最近 200 行，再持续跟随。部署详情容器日志从本次操作开始时间读取，部署进行中即建立订阅，尚未创建容器时等待可读取输出，容器重建时重新定位输出来源。各入口的初始时间范围沿用现有业务定位，统一功能不把它们强行改为同一个时间窗口。

CI Stage/CD 操作日志在任务终态后读取完最后输出并结束；容器日志在视图打开且来源有效时持续跟随，不因一次部署任务结束停止。短暂网络中断自动退避重连，文件按游标续读，容器补读 Docker 仍保留的输出；权限不足、目标修订变化等确定性错误停止重试并显示原因。容器重建和历史无法补齐时显示来源变化或缺口，不承诺恢复已被 Docker 清理的内容。

### 性能与实施边界

持续流需要分块传输、批量更新与有界展示缓存，超限提示并淘汰最早展示内容，已有持久化日志不受影响。展示上限、重连退避、心跳周期和批次大小是 Plan 中结合验证确定的工程参数，不作为当前业务未决事项。

本次暂不需要新的日志 UI 库或消息中间件。复用 Monaco、共享 UI、Bearer 认证和现有 SSE 处理经验，保留 generation/Abort、Project 授权与执行目标校验等成熟能力。收益主要来自实时读取和消除重复实现，而不是增加工具栏功能数量。

## Acceptance

- [ ] 上述六类 Web 日志入口复用共享日志阅读能力，公共操作和状态反馈一致；CI/CD 页面没有独立重复的同类加载、空态、错误和滚动实现。
- [ ] 工具栏、字号、主题、间距、抽屉宽度及错误展示符合项目共享样式；内嵌区域和抽屉保留各自布局但共享日志能力。
- [ ] Web 持续日志采用带现有身份认证的 Fetch + SSE；新增内容以增量方式接收与展示。
- [ ] CI 阶段、CD 操作和部署详情容器日志均在执行过程中开始持续读取；容器尚未创建时等待可读取输出，不能因任务未完成而阻止订阅。已完成任务的历史日志仍可读取。
- [ ] CI/CD 文件日志支持历史回放及游标续读，正常重连不重复、不遗漏已持久化输出；到达终态后读完最后输出再结束订阅。
- [ ] 容器日志支持持续输出，避免依赖每次替换最近 200 行；初始历史范围、重连补读及容器重建后的反馈在 Plan 中有明确约定。
- [ ] 已有内容时发生读取错误，内容仍保留，异常通过项目共享 Toast 提示；短暂故障自动恢复，日志控件不展示异常。正常完成、暂停跟随、无输出与连接中断不会相互混淆。
- [ ] 所有入口提供一致的跟随、搜索和读取恢复能力；上滚暂停跟随但继续接收输出，回到底部或主动恢复后继续跟随。
- [ ] 日志控件不提供复制能力，所有日志入口一致移除复制操作。
- [ ] 停止操作不展示容器日志的现有规则保留，其操作日志在停止任务执行过程中正常流式读取。
- [ ] local、Linux SSH、Windows SSH 通过各自既有执行目标读取；遵循 Project 成员及资源授权，目标变更时避免继续读取错误目标。
- [ ] 关闭日志视图、离开页面、切换 Project/目标正确释放订阅；旧事件不污染新视图，CI/CD 任务不受影响。
- [ ] 同一页面内关闭抽屉保留该资源的内容、游标与阅读位置；重开后补读，离页或切换 Project/目标时清理缓存。

## Risks and assumptions

- SSH CI 日志保存在目标环境，目标离线或修订/凭据变化后可能无法读取历史；流式传输不改变这个数据来源和可达性约束。
- Windows SFTP 已有文件共享冲突处理；持续读取需要沿用该平台约束，并正确取消阻塞读取和释放连接。
- 文件日志的字节 offset 与前端字符位置不同，需要处理跨块 UTF-8、最终输出读取及重连游标；当前整段字符串接口不能直接作为有界流实现。
- 容器日志缺少文件字节游标，重连、容器重建和 Docker 日志轮转后的完整性需单独定义，不承诺读取已被 Docker 删除的内容。
- 浏览器限速或大量输出可能积压，应避免订阅消费者拖住任务执行或无界占用内存。
- SSE 需要心跳、代理缓冲与连接超时处理；可参考部署对话，但不能沿用其固定请求时限作为持续日志订阅的默认生命周期。
- 用户已采纳工程默认方案；展示缓存、SSE 事件字段、读取批次、心跳和退避参数在 Plan 中确定。
