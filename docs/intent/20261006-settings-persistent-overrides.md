# 系统设置实际配置读取与持久化修改
最后修改时间: 2026-10-06 23:09:23

Review status: Draft

Mode: standard

## Background

Tencent 和 Oracle 的 Orbit 已作为普通应用运行，原 ENV 已补齐为 Version component 的同名占位符与 Service ENV 的真实值。相关迁移与 ENV 修正记录见 [迁移 Verification](../verification/20261006-component-user-group-add.md#env-configuration-correction)。ENV 修正尚未部署，本任务不改变该交接状态。

原系统设置支持读取 `.env`、修改及重置，保存后需要重启 Orbit 才生效。现有启动加载仍使用 `godotenv.Load`，进程 ENV 优先于文件；设置页仅从文件及内置定义拼装配置，没有反映进程实际生效值。补齐的 Service ENV 部署后，会压住同名文件修改；Oracle 原 `.env` 为只读挂载，也不能作为设置页的可写存储。

用户希望恢复这项能力：系统设置读取实际生效配置，保存修改到持久化配置文件，后续重启和重新部署均能保留修改。Orbit 继续作为普通应用，通过通用挂载使用文件，不依赖识别自身 Service 或回写部署管理方。

现状依据：`internal/config/config.go`、`internal/application/settings/usecase/service.go`、`internal/infrastructure/storage/local/envfile/store.go`、`internal/bootstrap/http.go`、`web/src/views/settings/Settings.vue`；受控文件首次初始化能力见 `internal/application/deployment/usecase/mount_env.go` 的 `IgnoreIfExists`。

## Goal

1. 系统设置读取当前进程实际生效的配置，区分已生效值与已保存但待重启生效的值；刷新页面后仍能正确显示待生效状态。
2. 将 Service ENV 明确为部署基线；设置页主动修改的项目写入独立、可写的持久化覆盖文件，不回写 Service ENV。
3. 统一配置优先级为持久化应用覆盖 > 进程 ENV > 内置配置。加载、设置读取、保存校验和重置使用一致规则。
4. 保存仍按原能力在重启后生效；重置删除应用覆盖，恢复部署基线或未配置时的内置值。
5. 覆盖文件使用普通持久化目录挂载；若配置为受控文件，使用可写挂载及 `ignore_if_exists=true`，仅首次初始化，后续部署保留应用写入内容。
6. 同时支持 Tencent 由本地 Orbit 项目远程管理，以及 Oracle 在远端普通应用内运行的场景；无需管理实例连接、服务绑定或控制面角色特例。
7. 所有应用配置项均作为普通项支持编辑、保存和重置，包括数据库连接、JWT、MCP、服务监听和 worker 等配置；不按启动、加密或敏感用途设置只读特例，仍执行统一的类型和有效性校验。

## Non-goal

- 不实现配置热更新、自动重启或 Orbit 替换自身容器的执行流程。
- 不实现远端设置页调用部署管理实例修改 Service ENV，不新增 Orbit 专用部署或目录占用豁免。
- 不因修改密钥自动重加密既有凭据，不因修改数据库连接自动迁移业务数据；本任务负责配置读写及重启后按新值加载，不扩展为任意宿主机文件管理。
- 不在本次意图记录中执行远端配置切换、部署、停机或迁移；真实操作按后续用户指令执行。
- 不扩展为新旧加载方式并行的兼容层，不自动把原 `.env` 的全部值变成应用覆盖项。
- 不操作用户浏览器，不管理用户开发服务器。

## User scenarios

1. 用户查看系统设置时，看到 Orbit 实际使用的值，包括来自容器 ENV 的配置，不把文件值或内置值误认为当前值。
2. 用户修改任一配置项，保存后看到待重启生效；刷新后状态保留，重启后实际值与保存值一致，数据库连接和 JWT 等项目遵循同一流程。
3. 管理方通过普通服务部署重建 Orbit，已挂载的覆盖文件保留，用户此前的应用配置继续生效。
4. 用户重置某项配置，删除其应用覆盖；重启后恢复 Service ENV 的基线，其他配置不受影响。
5. 部署基线发生变化时，没有应用覆盖的字段使用新基线；已有应用覆盖的字段继续使用覆盖值，页面能区分来源。

## Acceptance

- [ ] 仅通过进程 ENV 提供的配置能够在系统设置中准确展示；加载和展示使用一致的字段定义与类型。
- [ ] 所有应用配置项均提供普通编辑、保存和重置能力；数据库连接、JWT、MCP 等项目没有只读或禁止编辑特例，敏感标记不限制可编辑范围。
- [ ] 已保存值与当前进程生效值分开表达，页面刷新后待生效状态不丢失；不将保存成功描述为已经生效。
- [ ] 覆盖文件只记录主动修改项，位于实际可写且持久化的挂载中；不依赖容器临时文件系统。
- [ ] 保存前按最终合并配置进行类型和必要的关联校验；无效配置及文件写入失败不得报告成功，原已保存配置保留。
- [ ] 文件解析及序列化正确保留合法配置值；保存避免中断或并发写入造成文件损坏及无关字段丢失。
- [ ] 重启后覆盖项优先于同名 ENV；重置删除覆盖后恢复部署基线，并保持其他字段。
- [ ] 普通重新部署保留已写入的覆盖内容；若使用受控文件，验证首次初始化及 `ignore_if_exists=true` 的后续保留行为。
- [ ] HTTP、worker 和 MCP 的启动入口使用同一加载规则；独立进程仍需分别重启，不宣称已有进程自动更新。
- [ ] Tencent SSH 与 Oracle local DooD 的部署准备明确覆盖文件位置、运行身份权限、挂载属性、初始化及回退方式；实际部署与运行验证按后续授权执行，不以单元测试替代。
- [ ] 复用现有设置页和权限边界，保留项目共享 UI 与接口约定；实现后按仓库要求验证前后端及本次主要流程。

## Open questions

暂无需要用户确认的未决事项。用户明确所有配置都是普通项，数据库连接和 JWT 等配置统一允许编辑、保存和重置。

覆盖文件的可配置入口和最终路径、复用现有 data 目录还是显式受控文件挂载，在 Plan 中结合现有实现确定。`/app/data/config/overrides.env` 是部署示例，不是固定业务路径或新增默认兜底。

## Decisions

- 用户要求恢复原来的配置加载和修改能力，并要求先评估。
- 讨论收敛为系统设置读取实际生效值、保存持久化覆盖文件；Service ENV 保留为部署基线，重启后加载覆盖。
- 文件可复用现有持久化 data 目录；若用受控文件挂载，必须只首次初始化并保留应用写入，不新增专门识别 Orbit 的部署逻辑。
- “重置”表示删除应用覆盖并恢复部署基线，不保证回到内置配置值。
- 用户明确所有配置都是普通项，删除 JWT 只读建议及关键项编辑范围待定问题；所有配置遵循统一编辑流程和校验，不增加用途相关的只读限制。
- 用户指定 `specflow:specflow` 标准模式记录任务；新建独立 Intent，后续按 Intent -> Plan -> Implementation -> Verification 推进。

## Risk

- Service ENV 是部署基线，不能再把它单独视为最终运行值；设置页必须表达配置来源和覆盖状态。
- 若沿用原 `.env` 的全部内容作为最高优先级覆盖，会压住当前正确的 Service ENV，可能恢复过期配置或密钥。切换时应保留已确认基线，只记录主动修改项。
- 单文件 bind mount 与原子替换的文件保存方式可能冲突；计划需要核对实际保存与挂载方式，不能只改变文件优先级。
- 持久化覆盖会跨容器重建保留；回退镜像或改变部署基线时，须同时核对覆盖文件，保留备份和明确的恢复步骤。
- 启动关键配置错误可能导致重启后无法提供设置 API，不能依赖应用在线自救；需要保存校验与外部恢复路径。
- 修改 JWT 会影响已有凭据解密，修改数据库连接会改变使用的数据来源；这些是普通配置修改的实际影响，不构成禁止编辑的条件，也不隐含自动重加密或数据迁移。
- 实际配置文件权限依赖运行身份和目标挂载。Tencent 与 Oracle 的路径、文件访问属性应分别核查，不写入真实凭据。
