# Intent / 意图：服务状态检查
最后修改时间: 2026-10-14 11:12:46

## Review status / 审查状态

Accepted

## Background / 背景

用户可能在 Orbit 外停止或启动容器，Service 保存的最近执行状态因此与目标 Docker 不一致。服务列表需要显式检查入口，操作过程参考自定义路由同步弹窗，让用户看见每条记录的处理结果。

## Goals / 目标

- 检查当前 Project 环境内全部受管 Service，不受列表分页、搜索和状态筛选影响。
- 一次批量查询 Docker，然后顺序更新业务记录，逐条反馈成功、失败或无需变化。
- 查询失败不修改记录；活动部署或预览后变化的服务、环境不能被旧观测覆盖。
- 沿用现有工具条、共享 UI 控件和页面业务组件目录约定。

## Non-goals / 非目标

- 不启停、重建容器，不修改版本、目录、组件声明或 Deployment 结果。
- 不增加自动轮询、后台续跑、通用批处理框架、数据库迁移或大规模 UI 测试。

## User stories / scenarios / 用户故事 / 场景

- 在目标 Docker 手动停止或启动服务后，从服务列表打开状态检查，查看记录状态与容器观测状态，确认后逐条更新。
- 同一环境包含其他 Compose project，只处理本 Project 管理的 Service code。
- 执行过程中某条记录无法更新，弹窗保留原因并继续后续服务。

## Acceptance criteria / 验收标准

- A01：服务列表提供状态检查入口，弹窗覆盖当前环境全部受管服务。
- A02：每轮只执行一次 Docker 容器清单查询，按精确 Compose project 标签归属；排除 one-off 容器。
- A03：全部 running 且无 unhealthy 为 running，全部 exited/created 或容器缺席为 stopped，混合或异常状态为 faulted，沿用 Service 现有三个状态。
- A04：确认顺序更新，每条立即展示结果；失败继续，结束刷新列表，重新检查获取新快照。
- A05：Docker 查询失败不写入状态并保留具体命令诊断；活动任务、目标变化和服务运行绑定变化阻止旧快照写入。
- A06：公共控件复用既有样式与交互，业务弹窗位于服务页面组件目录；完成仓库要求的开发检查。

## Workload assessment / 工作量评估

工作量中等：跨运行观测、条件持久化、HTTP/proto 契约和前端弹窗，但只有一个端到端交付结果。复杂度集中于一次观测跨多个确认请求与任务接替写入竞争；风险是旧观测覆盖较新的业务状态。复用部署 runtime、Service 仓储和路由同步交互，在主会话串行实施；检查聚焦批量观测、状态归属和写入竞争，不穷举边界。

结论：保持单任务。接口与数据库条件紧密耦合，不建立独立 task 或分配表。

## Candidate tasks and dependencies / 候选子任务与依赖

不适用。

## Open questions / 待定问题

暂无需要用户确认的未决事项。

## Decisions / 决策

- 用户明确要求批量读取，不对每条 Service 重复调用 Docker。
- 使用弹窗预览和逐条确认反馈，参考现有 RouteSyncDialog。

## Risks / assumptions / 风险 / 假设

- 检查反映批量查询时刻的观测，无法锁住外部 Docker 操作。
- 服务端重启或快照过期后需要重新检查。
