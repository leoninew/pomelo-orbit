# Intent / 意图：GitHub Pages 文档首期
最后修改时间: 2026-10-30 15:40:41

## Review status / 审查状态

Accepted

## Background / 背景

项目已有 README、业务模型入口和大量研发过程记录，但缺少面向开源读者的独立文档入口。此前评估确定使用 GitHub Pages 提供文档；首期先验证从编写、构建、检查到发布和访问的完整流程，不一次建设完整手册。

GitHub 仓库 `leoninew/pomelo-orbit` 的默认分支为 `develop`，预计项目站点地址为 `https://leoninew.github.io/pomelo-orbit/`。本地 `develop` 当前跟踪 Gitee，变更进入 GitHub 才会触发 GitHub Actions；仓库尚需启用 Pages。

[旧文档中心意图](20260728-documentation-handbook.md)曾提出产品内 `/doc` 和不引入独立站点。本首期以 GitHub Pages 为交付方向，不以该草案的展示方式、全量章节或首版双语作为验收依据；旧草案保留供追溯。

## Goals / 目标

- 建立仓库内可维护的 Markdown 文档站，使用独立公开内容源，沿用项目 Node.js、Corepack 和 Yarn 工具链。
- 发布最小但真实的中文内容：首页说明项目定位和文档入口；至少提供一篇基于当前仓库核对的开发入门指南，展示前置条件、操作和验证方式。
- 建立本地构建、变更检查及 GitHub Pages 发布流程，并从仓库 README 提供文档入口。
- 验证项目子路径下的页面和静态资源可访问，以及研发过程记录不进入站点产物。

## Non-goals / 非目标

- 不开发产品内 `/doc`，不修改产品认证、前后端业务或发布包内容。
- 不要求首期覆盖安装、CI/CD、网关、SSH、MCP、安全运维、备份恢复等完整手册，也不以部署首个业务应用作为本期验收。
- 不要求首期提供全量中英文翻译、多版本文档、全文搜索、定制主题或复杂文档平台；后续按实际需求补充。
- 不将 `docs/intent`、`docs/plan`、`docs/verification`、`docs/archive` 等过程与历史材料作为站点正文或当前产品验收依据。

## User stories / scenarios / 用户场景

- 开源读者从仓库 README 打开公开文档，了解项目定位，进入开发入门文章并找到进一步的项目资料。
- 贡献者修改 Markdown 后，能按仓库说明安装依赖、构建文档，并在提交前发现基本构建或链接问题。
- 维护者将变更合入 GitHub 的发布分支后，文档自动发布；直接访问或刷新子页面时，页面和资源仍正常加载。

## Acceptance criteria / 验收标准

- A01：文档内容与研发过程记录隔离；构建产物不包含过程或归档 Markdown 对应的页面。公开仓库本身仍可访问这些文件，不将站点隔离描述为保密措施。
- A02：站点至少有中文首页和一篇非占位的开发入门文章；内容基于当前代码、配置和任务命令核对，说明前置条件、操作、验证方式和已知限制。README 提供文档入口，并修正本期涉及的失效开发命令。
- A03：使用仓库固定的文档依赖可在本地完成构建；构建及适用的链接检查失败时返回失败状态。操作说明包含命令运行目录和必要前置条件。
- A04：GitHub PR 具备文档构建检查且不部署；GitHub 发布分支的文档变更可通过 Actions 构建并部署到 Pages。部署权限仅授予需要发布的 job。
- A05：Pages 配置和站点资源适配 `/pomelo-orbit/`；实际发布后，首页及至少一个文章深链接可直接访问和刷新，导航、样式及资源正常，记录可核验的网址与结果。
- A06：文档正文明确其适用版本或开发状态；未核验的公开镜像、Release 下载和安装步骤不作为已验证事实发布。

## Workload assessment / 工作量评估

工作量中等：主要交付为最小站点、两类真实内容、仓库入口和 Pages 构建发布流程。职责涉及文档内容、独立前端构建配置、CI 权限与仓库设置，不涉及业务代码或数据迁移。

复杂度主要在 GitHub 项目站点子路径、独立内容扫描范围及 PR 与部署权限隔离；风险主要是 GitHub Pages 尚未启用、GitHub 与 Gitee 推送路径不同，以及开发文档与当前实现漂移。检查范围包括本地构建、内容和链接检查、workflow 配置，以及具备条件时的真实站点访问；审查需要 README、站点源与产物范围、锁文件、workflow 和实际发布证据。

结论：保持单任务。站点配置、最小内容和发布流程共同构成一次纵向闭环，均依赖同一内容路径与构建产物；拆分会增加共享配置和集成协调，首期无需建立 task。计划阶段仍需明确实施顺序和外部设置责任。

## Candidate tasks and dependencies / 候选子任务与依赖

不适用；不创建 task。

## Open questions / 待定问题

- 实际启用 Pages、向 GitHub 推送和验证公开站点，需要届时具备相应仓库权限和明确的执行授权；若不可执行，记录阻塞与待办，不将本地构建或 workflow 配置当作已完成线上验收。

## Decisions / 决策

- 使用现有 GitHub 仓库的 Project Pages；不新建 `*.github.io` 仓库，不建设产品内文档中心。
- 以仓库内 Markdown 为内容来源，使用 VitePress 稳定版建立独立静态站点；具体版本、依赖布局、目录和 workflow 在计划中确定。
- 首期先交付中文最小内容和发布闭环；双语、完整用户手册和搜索等能力后续单独评估。
- 站点从 GitHub 发布分支构建，清楚标注开发状态或适用版本；首期不建立多版本站点。

## Risks / assumptions / 风险 / 假设

- Pages 的仓库设置、权限、Actions 配额或实际发布目标可能影响上线，不能仅凭 workflow 文件推断站点已经可用。
- GitHub 项目站点位于仓库子路径；错误的 base 或硬编码根路径会造成深链接、脚本和图片失效。
- 文档站只纳入明确指定的公开内容；现有仓库仍为公开仓库，排除导航或产物不能隐藏仓库文件。
- 现有 README 中开发启动命令与 Taskfile 不一致；首期内容必须对照当前代码核对，不复制旧草案中的过时路径与能力描述。
- 文档站依赖和构建缓存应避免进入产品包或扩大 Docker 构建上下文；不改变现有产品交付流程。
