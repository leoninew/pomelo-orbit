# API 盘点需求
最后修改时间: 2026-07-01 15:29:44

## Review status

Accepted

## Background

当前需要对项目现有 API 做一次摸底，形成可审阅的接口清单，帮助后续前后端联调、文档补齐、CORS/base URL 配置或 API 契约治理等工作建立基础认知。

用户特别关注：部分接口可能没有遵从 `Req` / `Resp` 形式定义请求或响应，部分接口可能直接返回数组、字典或框架通用结构，需要在盘点结果中标记出来。

## Goal

- 盘点当前代码库中已经实现或明确暴露的后端接口。
- 对每个后端接口记录：请求方法、路径、请求体、响应体。
- 请求体与响应体重点记录“名称和定义来源”，不展开具体字段清单。
- 响应体需要标明是否遵从 `Resp` 形式；如果直接返回数组、字典、匿名结构、基础类型或框架通用响应，需要单独标记。
- 请求体需要标明是否遵从 `Req` 形式；如果没有请求体、直接读取 query/path/form、匿名结构或未显式绑定请求结构，需要单独标记。
- 增加前端相关说明：标记前端是否存在对应调用、调用封装位置、前后端路径或契约是否存在明显不一致。
- 尽量从代码实现、路由注册、请求/响应结构体、处理函数、前端调用封装和已有文档中提取信息，而不是凭空推测。
- 对无法从代码中确定的请求体或响应体，明确标注“不确定”“无请求体”“未在代码中显式定义”或类似结论。

## Non-goal

- 不修改产品代码、路由行为、请求/响应结构或鉴权逻辑。
- 不为 API 设计新契约，也不做兼容层、别名或默认值兜底。
- 不主动启动、停止或重启开发服务器。
- 不执行 Git 写操作。
- 不承诺覆盖部署环境、网关、反向代理或第三方服务实际暴露的所有接口，除非这些信息能从当前代码库或用户提供资料中确认。
- 不展开请求体或响应体的具体字段级文档；本次只记录名称、定义来源和形态。

## User scenarios

- 作为开发者，我希望看到项目目前有哪些后端接口，便于判断前端、后端和部署配置是否一致。
- 作为维护者，我希望知道每个后端接口的请求方法和路径，便于后续整理正式 API 文档。
- 作为调用方，我希望了解请求体和响应体的名称、定义来源和是否符合 `Req` / `Resp` 约定，便于联调和排查契约不一致问题。
- 作为前端开发者，我希望知道前端代码中是否已有对应调用，以及调用位置与后端接口是否匹配。

## Acceptance

- 输出一份 API 盘点结果，至少包含：请求方法、路径、请求体、响应体。
- API 来源需要可追溯，优先引用相关代码文件或路由定义位置。
- 对同一路径的不同请求方法分别列出。
- 请求体记录名称和定义来源；如果不存在、未绑定、匿名、非 `Req` 形式或无法静态确认，需要明确标注。
- 响应体记录名称和定义来源；如果不存在、匿名、非 `Resp` 形式、数组、字典、基础类型、框架通用结构或无法静态确认，需要明确标注。
- 增加前端相关说明，至少说明是否发现前端调用、调用位置，以及明显的前后端路径或契约差异。
- 如发现路由定义、处理函数、请求/响应类型、前端调用之间存在不一致或无法确认之处，单独列为风险或待确认项。

## Open questions

- 输出结果按 SpecFlow 文档落实，当前理解为在 `docs/` 下生成过程文档或盘点文档；具体落在哪个阶段文档或是否另建 inventory 文档，需要在计划阶段确定。
- 盘点范围已限定为后端接口；前端只作为调用侧说明，不把前端路由、静态资源或页面路径当作 API 盘点对象。
- 当前不需要记录响应体具体字段；只记录响应体名称和定义来源。
- 当前不要求记录鉴权、请求头、路径参数、查询参数、状态码和错误响应，除非它们对识别请求体/响应体形态或前端调用差异有直接帮助。
- 是否以当前代码库为唯一事实来源，还是需要结合线上环境、部署配置或外部 API 网关配置？当前默认以当前代码库为准。

## Decisions

- 本阶段按“当前代码库静态盘点后端接口”理解任务范围。
- 输出按 SpecFlow 需求文档落实。
- 先聚焦用户明确要求的四类信息：请求方法、路径、请求体、响应体。
- 请求体/响应体只记录名称、定义来源和形态，不展开具体字段。
- 需要显式标记不符合 `Req` / `Resp` 形式的接口，以及直接数组、字典、匿名结构等返回形态。
- 需要补充前端相关说明，但前端说明服务于后端接口盘点，不扩大为前端路由盘点。
- 未经用户进一步确认，不修改产品代码、不生成正式 OpenAPI 契约、不运行或管理开发服务器。

## Risk

- 部分 API 的响应体可能由运行时组合、框架中间件、通用错误处理或第三方库生成，静态盘点可能只能给出近似结构或来源说明。
- 如果路由注册分散在多个模块，可能需要较系统地搜索路由定义和 handler，存在遗漏风险，需要在后续计划中明确搜索策略。
- 如果前端存在调用未被后端实现的接口，或后端存在未被前端调用的接口，需要在盘点结果中区分“后端实现存在”和“前端调用存在”。
- 不展开字段级定义会降低契约完整性，但符合本次用户指定范围。
