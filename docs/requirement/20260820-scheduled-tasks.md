# 计划任务与定时调度
最后修改时间: 2026-08-20 23:25:36

Review status: Draft
Flow mode: strict

## Background

当前 Orbit 已有数据库持久化的 `background_task` 队列、可独立运行的 Worker，以及 Pipeline Run 和 Deployment 的异步执行能力。Worker 通过 `worker.poll_interval` 轮询并领取已经入队的任务，但系统还没有面向用户的计划任务实体、cron 调度、下次执行时间或计划执行历史。

用户需要能够让已有的 Pipeline、Deployment 等业务动作在指定时间或周期自动触发。计划任务应能够跨进程重启恢复，并继续复用现有后台队列的租约、重试和执行记录能力。

## Goal

1. 增加持久化的计划任务能力，支持一次性执行和周期性 cron 执行。
2. 允许用户为计划任务选择受支持的业务动作，例如触发 Pipeline、部署或重启 Service；计划任务不直接承载业务执行逻辑。
3. 提供计划任务的创建、编辑、启用、禁用、立即触发和执行历史查询能力。
4. 计划任务在应用重启、独立 `serve`/`worker` 进程运行以及多个 Worker 实例并存时，不丢失任务且不会因为调度竞争产生重复入队。
5. 复用现有 `background_task` 执行链路，让 Scheduler 只负责“何时产生任务”，现有 Worker 继续负责“如何执行任务”。

## Non-goal

- 不把计划任务扩展为完整的 Workflow Engine、人工审批流或跨系统补偿平台。
- 不允许用户提交任意 `task_type`、任意代码或任意基础设施命令；业务动作必须由应用层显式白名单化。
- 第一阶段不引入 Redis、Temporal 或其他外部调度基础设施，不替换现有数据库任务队列。
- 第一阶段不支持秒级 cron、复杂补偿编排、跨计划任务依赖和无限制的历史补跑。
- 不将 Pipeline 或 Deployment 的业务规则复制到 Scheduler、HTTP Handler 或数据库适配层。

## User scenarios

1. 项目管理员创建一个计划任务，在指定时区的指定时间触发一次 Pipeline。
2. 项目管理员创建一个 cron 计划，周期性触发已绑定 Repository 的应用 Pipeline。
3. 项目管理员创建一个周期性部署或重启任务，并能看到每次计划执行对应的后台任务、状态和错误信息。
4. 管理员暂时禁用计划任务；禁用后不再产生新的后台任务，但已经入队的任务继续按既有队列语义处理。
5. 管理员手动立即触发一次计划任务；该次触发应有独立的执行记录，不应破坏下一次计划时间。
6. Orbit 在计划到期前后重启，或同时运行多个调度进程；计划仍能被可靠处理，单次计划时间最多产生一个执行任务。
7. 计划触发的 Pipeline 或 Deployment 执行失败时，复用现有后台任务重试和失败状态，计划本身仍保留并按其调度策略计算下一次执行时间。

## Acceptance

- [ ] 系统持久化计划任务的目标、触发方式、时区、启用状态和下一次执行时间。
- [ ] 第一阶段支持一次性计划和 5-field cron 计划；计划时间统一以 UTC 持久化，并保留用户选择的 IANA 时区用于计算和展示。
- [ ] 系统只允许受支持的业务动作进入计划任务，且创建、编辑、立即触发和查询都执行项目权限校验。
- [ ] 到期计划会生成现有 `background_task`，并由现有 Worker 执行；Scheduler 不直接执行 Pipeline 或 Deployment 业务流程。
- [ ] 计划抢占、计划执行记录创建、后台任务入队和下一次执行时间更新具备原子性；调度进程崩溃后不会出现已推进时间但没有任务的状态。
- [ ] 多个 `serve`/`worker` 进程同时调度时，同一个计划时间不会重复入队。
- [ ] 计划任务支持启用、禁用、编辑、立即触发，并能查询计划执行历史及关联后台任务。
- [ ] 计划到期错过、重复执行、并发执行、时区和夏令时等边界行为有明确策略并覆盖测试。
- [ ] SQLite 与 MySQL 均支持计划任务的持久化和并发抢占，不修改已执行迁移文件。
- [ ] 调度失败、入队失败和计划执行失败有结构化日志及可定位的错误信息。

## Open questions

- 计划任务的第一阶段是否只允许 Pipeline 触发和 Deployment 操作，还是同时开放其他业务动作？
- cron 是否固定为 5-field，还是需要支持包含秒字段的 6-field 表达式？
- 未配置时区时，默认使用 UTC、系统时区，还是项目时区？
- 计划错过执行时间时，默认跳过、补执行一次，还是按错过次数补齐？是否允许用户逐计划选择策略？
- 同一计划已有任务处于 pending/running 时，下一次到期应跳过、延后还是允许并行？
- 一次性计划执行成功后自动禁用，还是保留为已完成的不可再次触发记录？
- 计划任务归属 Project，还是允许跨 Project 管理？对应的权限名称和角色默认授权需要确定。
- 是否需要保留计划定义变更前后的快照，以便解释历史执行当时使用的目标和参数？
- 计划执行历史是否复用 `background_task` 查询，还是提供独立的 `schedule_run` 业务记录和状态模型？

## Decisions

- 计划任务采用“数据库持久化计划 + Scheduler 到期入队 + 现有 Worker 执行”的总体方向。
- Scheduler 使用标准库 `time.Ticker` 作为唤醒机制；cron 表达式解析和下一次时间计算优先评估 `github.com/robfig/cron/v3`，不使用仅存在于进程内的调度器作为持久化来源。
- 计划任务与后台任务分离建模：计划描述未来触发规则，`background_task` 描述一次具体执行。
- 计划任务应通过应用层用例和受支持的 typed action 调用现有 Pipeline/Deployment 能力；Scheduler、HTTP Handler 和数据库 Repository 不新增业务执行分支。
- 多进程安全依赖数据库条件抢占或事务锁，不依赖“系统中只有一个 Scheduler”这一运行假设。
- 本 Requirement 只记录需求和初步方向；具体表结构、事务边界、调度租约、misfire/concurrency 语义留到 Spec 阶段确定。

## Risk

- SQLite 与 MySQL 的行锁、事务和并发更新语义不同，计划抢占实现可能需要方言适配和双数据库集成测试。
- 服务重启、网络抖动或事务提交前崩溃可能导致重复触发或漏触发，必须以唯一执行键和原子入队防护。
- 时区和夏令时会影响 cron 的“下一次执行”计算；未明确策略前不能把系统本地时间作为隐式默认。
- 计划任务如果复用通用任务类型输入，可能绕过业务权限或创建不可安全执行的任务；动作白名单必须早于实现确定。
- Pipeline、Deployment 本身存在运行中状态和幂等约束，计划的并发策略不能只由 Scheduler 的时间逻辑决定。
- 现有工作树存在其他未提交改动，本需求文档不应将其混入后续实现范围。
