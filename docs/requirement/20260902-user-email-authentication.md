# 用户邮箱认证与关联约束调整
最后修改时间: 2026-09-02 16:50:24

Review status: Accepted

## Background

现有用户模型允许空邮箱、使用用户名密码登录，并以数据库物理外键维护用户与角色、项目成员、登录历史和部署对话创建人的关系。产品要求改为以邮箱作为登录标识，并把用户业务关联约束收敛到应用层。

## Goal

- 登录请求使用 `email + password`；用户名保留为展示与管理字段，不再作为登录凭据。
- 用户邮箱必填、规范化为小写并校验格式，使用普通唯一索引保证唯一性。
- 密码长度统一限制为 6–36。
- 移除所有引用 `user` 的物理外键；删除用户时由业务层清理用户角色和项目成员，保留登录历史与部署对话历史。
- 三种数据库驱动的管理员 seed 统一为 `admin@lvh.me` / `admin@lvh.me`，并离线更新本地 MySQL 开发库。

## Non-goal

- 不删除或重命名用户名字段。
- 不保留用户名登录兼容路径，也不新增兼容迁移。
- 不引入额外密码规则 helper 或兼容分支。

## User scenarios

- 管理员使用 `admin@lvh.me` 与 `admin@lvh.me` 登录。
- 管理员创建或编辑用户时必须提供有效邮箱。
- 管理员删除非当前用户时，其角色和项目成员关系被清理；历史登录和对话记录仍可保留用户 ID 快照。

## Acceptance

- API、Proto、前端登录和用户管理界面均使用邮箱字段。
- `user.email` 为非空且唯一，用户引用外键不存在。
- 用户删除复用 HTTP 写请求事务切面，不引入用户域额外的 `TransactionRunner`。
- 本地 MySQL 管理员记录、邮箱列和引用外键与当前模型一致。
- 生成、后端测试和前端检查通过。

## Open questions

暂无需要用户确认的未决事项。

## Decisions

- 用户确认直接修改历史 seed / migration，并按离线数据库更新处理。
- 事务由既有 HTTP 写请求切面统一提供；业务层只协调跨表删除顺序。

## Risk

- 历史 migration 已被原地修改，已有非本地数据库不会自动重放这些变更；需要按本地开发库相同方式离线处理。
